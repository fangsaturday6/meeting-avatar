# 音频采集与前端信号处理（macOS · Electron + Python · 截至 2026-11）

> 说明：开源项目的结论来自 2026-11-12/13 直接读各仓库 main 分支源码（链接指向具体文件）；Chromium/Electron 的结论来自对应版本的源码和官方文档。
> 仓库改名提示：`Zackriya-Solutions/meeting-minutes` 现为 `Zackriya-Solutions/meetily`；`fastrepl/hyprnote` 现为 `fastrepl/anarlog`（下文仍称 Hyprnote）；`mediar-ai/screenpipe` 现为 `screenpipe/screenpipe`。
> 本项目现状（只读核对）：Electron 43.3.0（对应 Chromium 150.0.7871.212）；`app/main.js` 已设 `backgroundThrottling: false`；`app/pack.js` 只写了 `NSMicrophoneUsageDescription`，没有 `NSAudioCaptureUsageDescription`。

## 1. macOS 上采集系统/应用声音有哪些路子，各自的权限、系统版本、稳定性；同类项目各用哪种；有没有现成库

### Takeaway
2026 年的主流已经从 ScreenCaptureKit 转向 Core Audio process tap（macOS 14.2+，实际建议 14.4+）：Meetily、Hyprnote 默认都用 tap，Chromium/Electron 自 Electron 39 起也默认用 tap；ScreenCaptureKit 只作为老系统兜底，虚拟声卡（BlackHole）是最后手段。对本项目（Electron 43）而言，系统声音可以不写一行原生代码，直接用 `getDisplayMedia` + `audio: 'loopback'` 拿到，但必须在 Info.plist 加 `NSAudioCaptureUsageDescription`，且权限缺失时只会得到一条"死"音轨、没有任何报错。

### Cited Findings

**A. Core Audio process tap（`AudioHardwareCreateProcessTap` + 私有聚合设备）**
- Apple 官方示例说明：tap 可指定抓哪些进程、可选 mono/stereo 混音、可设为私有、可让被抓进程静音；用法是把 tap 加进一个 HAL 聚合设备当输入用；要求 macOS 14.2+，Info.plist 必须有 `NSAudioCaptureUsageDescription`，第一次从含 tap 的聚合设备开始录音时系统才弹"系统音频录制"授权 — [Apple: Capturing system audio with Core Audio taps](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps)
- screenpipe 把 tap 的最低版本定为 14.4 而不是 14.2，理由写在源码注释里：14.2–14.3 上授权弹窗落在另一个 TCC 类别、提示文案不一致，权限处理不可靠；Apple 的规范示例 AudioCap 也以 14.4+ 为目标 — [screenpipe process_tap/macos.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/process_tap/macos.rs)；[insidegui/AudioCap（"Sample code for recording system audio on macOS 14.4+"）](https://github.com/insidegui/AudioCap)
- 权限被拒/缺 plist 键时完全静默：所有 Core Audio 调用返回 `noErr`，IOProc 照常每秒触发数百次，但缓冲区全是 0；一个上线产品（Thunder Kitty）因 Xcode 没把 `INFOPLIST_KEY_NSAudioCaptureUsageDescription` 写进编译产物而踩坑。仅创建 tap 不会弹授权，要把 tap→聚合设备→IOProc→`AudioDeviceStart` 整条链路跑起来才弹；授权弹窗文案是"System Audio Recording"而不是"Screen & System Audio Recording" — [dev.to: 2,000 Buffers of Nothing（2026-06）](https://dev.to/nickdelv/2000-buffers-of-nothing-3i8)
- 同一篇文章指出 tap 相对 SCK 的覆盖面优势：SCK 工作在应用/合成器层，能抓 Zoom、Meet、浏览器，但抓不到后台守护进程的声音（`callservicesd` 的 iPhone 接力通话、`avconferenced` 的 FaceTime）；tap 在 HAL 层，能看到流向输出设备的所有声音 — [dev.to: 2,000 Buffers of Nothing](https://dev.to/nickdelv/2000-buffers-of-nothing-3i8)
- Meetily 的 tap 实现注释：用"mono global tap、不排除任何进程"；聚合设备里**只放 tap，不要同时放输出设备**，否则同一路声音进来两遍（表现为回声）；权限被拒时 tap 返回全零 — [meetily capture/core_audio.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/capture/core_audio.rs)
- Recall.ai（卖桌面录制 SDK 的厂商，有立场）评价：tap 文档少，很多开发者难以在生产环境做稳 — [Recall.ai: How to get access to system audio（2026-05，2026-10 更新）](https://www.recall.ai/blog/how-to-get-access-to-system-audio)

**B. ScreenCaptureKit 音频**
- `SCStreamConfiguration.capturesAudio` 自 macOS 13.0 起可用，默认不采音频 — [Apple: capturesAudio](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/capturesaudio)；`captureMicrophone` 自 macOS 15.0 起可用 — [Apple: captureMicrophone](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/capturemicrophone)
- SCK 的音频绑在一次屏幕捕获会话上，即使只要声音也得配置一个显示器/窗口/应用作为目标；需要"屏幕录制"权限 — [Recall.ai](https://www.recall.ai/blog/how-to-get-access-to-system-audio)
- macOS 15 Sequoia 起，屏幕录制权限会周期性重新确认（测试版每周，后改为每月，弹窗有"Allow For One Month"）；有开发者实测纯 SCK 应用同样被弹 — [9to5Mac 2024-08-14](https://9to5mac.com/2024/08/14/macos-sequoia-screen-recording-prompt-monthly/)
- Chromium 源码直接写明：SCK 系统回环采集"在 macOS 15.0 上因授权弹窗问题被禁用"，只有打开 `MacSckSystemAudioLoopbackOverride` 才启用；而 tap 路径只要 macOS ≥ 14.2 就支持 — [chromium main media_switches.cc](https://github.com/chromium/chromium/blob/main/media/base/media_switches.cc)
- screenpipe 记录的 SCK 稳定性问题（源码注释）：(1) 睡眠唤醒后 SCK 返回空显示器列表，导致"System Audio (output) not found"；(2) SCK 流锚定的显示器失效（合盖外接屏、拔显示器、KVM 切换）时，音频流**静默停止回调**，cpal 不报错，`/health` 仍显示正常，会议里对方的声音从此丢失（其 issue #3901）；(3) Sequoia（Darwin 24.3+）上 SCK 在正常空闲（没东西在放）时也不回调，所以不能用简单超时判断死活——他们的做法是 45 秒静音 + "可用显示器集合发生变化"才重建流 — [screenpipe sck_output_watchdog.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/sck_output_watchdog.rs)；[screenpipe process_tap/macos.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/process_tap/macos.rs)

**C. Electron / Chromium 的系统声音回环（本项目最相关）**
- Electron 官方文档（v43.3.0 的 desktop-capturer.md）：macOS 14.2+ 必须加 `NSAudioCaptureUsageDescription` 才能采到音频；从终端/IDE 里未打包运行时，这个键要在**父程序**（终端）的 Info.plist 里；自 Electron `v39.0.0-beta.4` 起 Chromium 默认用 CoreAudio Tap API 做桌面音频采集，tap 创建失败**不会**回退到旧的"屏幕与系统音频录制"路径；权限缺失时仍会创建一条"死"音轨，没有任何警告或报错；想继续走旧权限可 `disable-features=MacCatapLoopbackAudioForScreenShare` — [Electron v43.3.0 desktop-capturer.md](https://github.com/electron/electron/blob/v43.3.0/docs/api/desktop-capturer.md)
- Electron main 分支文档补充：自 Electron 45 起 `MacCatapLoopbackAudioForScreenShare` 开关已被上游移除、不再生效；macOS 12.7.6 及更低版本无法采系统声音，只能走 BlackHole/Soundflower 虚拟设备 — [Electron main desktop-capturer.md](https://github.com/electron/electron/blob/main/docs/api/desktop-capturer.md)
- Electron 43.3.0 对应 Chromium 150.0.7871.212 — [electron v43.3.0 DEPS](https://github.com/electron/electron/blob/v43.3.0/DEPS)；该版本源码中 `kMacCatapLoopbackAudioForScreenShare` 为默认开启 — [chromium 150.0.7871.212 media_switches.cc](https://github.com/chromium/chromium/blob/150.0.7871.212/media/base/media_switches.cc)
- 用法：主进程 `session.setDisplayMediaRequestHandler` 的回调里传 `audio: 'loopback'`（或 `'loopbackWithMute'`），渲染进程调 `getDisplayMedia`。**文档自相矛盾**：v43.3.0 的 session.md 仍写着 loopback"目前只支持 Windows"，与同版本 desktop-capturer.md 的 macOS 说明冲突，以后者和 Chromium 源码为准 — [Electron v43.3.0 session.md](https://github.com/electron/electron/blob/v43.3.0/docs/api/session.md)
- 社区包 `electron-audio-loopback` 适用 Electron ≥31 且 <39（README 明说 39+ 不再需要它）；做法是 `getDisplayMedia` 必须带 `video: true`，拿到流后把视频轨删掉，只留音频；README 警告不删视频轨可能出 bug — [alectrocute/electron-audio-loopback](https://github.com/alectrocute/electron-audio-loopback)；作者博文说明了背后的隐藏开关（`MacLoopbackAudioForScreenShare`、`MacCatapSystemAudioLoopbackCapture`、`MacSckSystemAudioLoopbackOverride`），并指出同时采视频时有一个 macOS 屏幕捕获 bug — [alec.is 2025-08-02](https://alec.is/posts/bringing-system-audio-loopback-to-electron)

**D. 虚拟声卡（BlackHole 等）**
- BlackHole：零额外驱动延迟，支持 macOS 10.10+，支持 8k/16k/44.1k/48k 等采样率；安装包装完要重启；要"又听得到又录得到"需用户在"音频 MIDI 设置"里建多输出设备，且 macOS 不支持调多输出设备的音量，内建输出必须排在多输出设备第一位；非 GPLv3 项目要捆绑需另买许可 — [ExistentialAudio/BlackHole README](https://github.com/ExistentialAudio/BlackHole)
- Electron 博文作者对这条路的评价：fork BlackHole、自定义驱动、聚合设备、自动切输入这些做法"脆弱且烦人" — [alec.is](https://alec.is/posts/bringing-system-audio-loopback-to-electron)

**E. 同类项目用的哪一种**
- **Meetily**（Tauri/Rust，MIT，3.2 万星）：两个后端可在设置里切——ScreenCaptureKit（通过 cpal 的 SCK host）和 Core Audio（cidre 绑定的 tap + 聚合设备）；**macOS 默认是 Core Audio tap** — [meetily capture/backend_config.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/capture/backend_config.rs)；[meetily Cargo.toml（cpal 固定到 RustAudio/cpal 某提交 + cidre）](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/Cargo.toml)
- **Hyprnote / anarlog**（Tauri/Rust，MIT）：系统声音只走 Core Audio tap（cidre，mono global tap + 私有聚合设备），麦克风走 cpal — [anarlog audio-actual/src/speaker/macos.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/src/speaker/macos.rs)；[anarlog audio-actual/Cargo.toml](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/Cargo.toml)
- **screenpipe**（Rust；GitHub 许可证字段为 NOASSERTION）：系统声音**默认 ScreenCaptureKit**（自家 cpal fork），Core Audio tap 是可选项（14.4+）；另有"按进程的会议 tap"——先用 `kAudioProcessPropertyDevices` 查出会议进程正在用哪个输入设备、是否在出声，再只抓该进程 — [screenpipe sck_output_watchdog.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/sck_output_watchdog.rs)；[screenpipe meeting_audio/macos.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/meeting_audio/macos.rs)；[screenpipe-audio Cargo.toml](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/Cargo.toml)
- **Granola**（闭源）：官方文档只说"用电脑的麦克风和系统声音转写，没有会议机器人"，要的权限叫"Screen & System Audio Recording"，并声明只为拿系统声音、不录视频；具体 API 官方没说 — [Granola: transcription issues](https://docs.granola.ai/article/transcription-issues)；[Granola + Webex 指南](https://www.granola.ai/blog/granola-cisco-webex-bot-free-meeting-notes)

**F. 可直接用的开源库**
- Swift 命令行 + Node 封装：**AudioTee**（Core Audio tap，macOS 14.2+；往 stdout 写原始 PCM，默认单声道、32 位浮点、每块 200 ms，`--sample-rate 16000` 时输出 16 位整型；支持按 PID 包含/排除、`--mute`；只支持默认输出设备；README 自称 API 不稳定；某些终端不弹授权导致"跑着但录不到"），Node 封装包 `audioteejs` — [makeusabrew/audiotee](https://github.com/makeusabrew/audiotee)
- Rust：`cidre`（Apple 框架绑定，MIT，Meetily/Hyprnote/screenpipe 三家都用它调 tap）— [yury/cidre](https://github.com/yury/cidre)；`screencapturekit-rs`（Apache-2.0）— [doom-fish/screencapturekit-rs](https://github.com/doom-fish/screencapturekit-rs)；`cpal`（最新 v0.18.2，2026-08）— [RustAudio/cpal releases](https://github.com/RustAudio/cpal/releases)
- Python：`ProcTap` 目前只有 Windows（WASAPI 进程回环），macOS 支持仍是"planned" — [m96-chan/ProcTap](https://github.com/m96-chan/ProcTap)

### Inferences
- 本项目是 Electron 43（Chromium 150），**最省事的路是 Chromium 自带的 tap 回环**：主进程注册 `setDisplayMediaRequestHandler` 回 `audio: 'loopback'`，渲染进程 `getDisplayMedia` 后丢掉视频轨，得到的系统声音 `MediaStream` 可以直接复用现有的 AudioWorklet → WebSocket 链路（另开一路 WS 或在帧头加通道标记）。前提：`pack.js` 加 `NSAudioCaptureUsageDescription`；开发时从终端 `npx electron .` 运行，权限会记在终端头上。
- 备选是另起一个 AudioTee 子进程（或自己写的 Swift 小工具）把 16k PCM 直接从 stdout 喂给 Python 后台，绕开渲染进程。好处：不依赖 Chromium 的开关变动、不需要屏幕源；代价：多一个要签名/公证的二进制，TCC 权限归属更绕。Hyprnote/Meetily/screenpipe 三家都在原生层自己调 tap，说明这条路是"做稳"的主流。
- 因为"权限缺失 = 静默全零/死音轨"是多方一致的行为（Apple tap、Electron 文档、Thunder Kitty 实测），**必须自己做"系统声音确实有非零数据"的探测**，不能靠 API 返回值。
- 现有"线上会议"模式依赖虚拟声卡（`audio.js` 注释），换成 tap 回环后可以去掉让用户装 BlackHole、建多输出设备这一步。
- 数字人自己用扬声器说的话也会出现在系统回环里（全局 tap 不排除任何进程）。可用 tap 的"排除进程"能力把本应用排除，或在后台按"正在播放"时间窗丢弃；Chromium 回环路径是否能排除自身（源码里有 `IsRestrictOwnAudioSupported`，mac 上取决于 tap 支持）未实测。

### Gaps
- Electron 43 上 `setDisplayMediaRequestHandler` 能否**只给 audio 不给 video 源**（从而完全不碰"屏幕录制"权限）未核实；`electron-audio-loopback` 的做法是仍然请求 video 再删轨。`desktopCapturer.getSources` 本身是否触发屏幕录制授权需要在打包后的应用里实测。
- "系统音频录制"（tap）权限是否像屏幕录制那样在 Sequoia/Tahoe 上每月重新确认：没找到 Apple 文档或可靠一手来源，未核实。
- Granola 实际用 tap 还是 SCK：只有 Reddit 评论和第三方评测的说法，互相矛盾，未核实。
- tap 路径的端到端延迟没有找到任何项目给出的实测数字。
- Apple 文档站点在本机代理下多次连接被拒，`AudioHardwareCreateProcessTap`、`excludesCurrentProcessAudio` 等页面未能直接读取，相关结论转引自各项目源码注释。

## 2. 「麦克风一路 + 系统声音一路」分开采集的好处，以及各项目怎么混音/对齐/分别识别

### Takeaway
三家都是两路分开采、各自重采样后在应用层按时间对齐；区别在下游：Hyprnote 把两路当**双声道**分别送识别并分别落盘（天然区分"我/对方"，且系统声音这一路就是 AEC 的参考信号），Meetily 则把两路混成一路再做 VAD 和识别（简单但丢了说话方信息）。对齐是这一环最容易出问题的地方，Hyprnote 和 screenpipe 都专门写了漂移/滞后估计和"某一路没来时补静音"的逻辑。

### Cited Findings
- **Hyprnote**：采集层有 `Joiner`，麦克风块和扬声器块各进一个队列（上限 30 块，溢出丢最旧并打 `mic_queue_overflow` 日志），成对弹出；某一路没就绪时用等长静音补齐另一路，而不是阻塞 — [anarlog capture/joiner.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/src/capture/joiner.rs)
- Hyprnote 下游有三种通道模式 `MicOnly / SpeakerOnly / MicAndSpeaker`；双路模式下向识别器发 `AudioDual(mic, spk)`，向录音器也发 `AudioDual`，即两路**不混音**、作为两个声道分别处理 — [anarlog listener-core source/pipeline.rs](https://github.com/fastrepl/anarlog/blob/main/crates/listener-core/src/actors/source/pipeline.rs)
- Hyprnote 有独立的 `audio-sync` crate：`LagTrendTracker` 根据两路滞后量随时间的变化估算漂移，输出 `drift_ppm`、`drift_ms_per_min`（单元测试里的例子是 10 秒漂 8 个采样 = 50 ppm）— [anarlog audio-sync/src/drift.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-sync/src/drift.rs)
- Hyprnote 的 AEC 参考对齐参数（源码常量）：参考信号最大滞后 600 ms、最小重叠 400 ms、最小相关度 0.12、参考/麦克风 RMS 低于 1e-4 不处理；设备切换时重置 AEC 和对齐器 — [anarlog capture/stream.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/src/capture/stream.rs)
- **Meetily**：`AudioMixerRingBuffer` 按固定窗口（代码里是 600 ms，注释仍写 50 ms）从麦克风和系统两个缓冲各取一窗，不够就补零；混音器不做 ducking，系统声音略降、求和后软限幅；**混音后的单路**送 VAD + Whisper/Parakeet；落盘也只存混音（"we only store mixed audio"）— [meetily audio/pipeline.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/pipeline.rs)；[meetily audio/incremental_saver.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/incremental_saver.rs)
- Meetily 在实时路径把 VAD 的"静音多久算一句结束"定为 500 ms，注释解释：离线路径用 2000 ms，但在连续的系统声音下 2000 ms 会让一个 VAD 段一直不关、实时字幕出不来 — [meetily audio/pipeline.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/pipeline.rs)
- **screenpipe**：AEC 处理器给麦克风样本和扬声器回环样本都带采集时间戳，按 10 ms（160 样本 @16k）阈值对齐；扬声器超前就丢旧的扬声器样本，麦克风超前就丢旧的麦克风样本并保留远端参考；队列最多留 1 秒（"过期的参考比旁路更糟"）；没有扬声器数据时走旁路模式（只做降噪和增益）避免引入延迟；输出是 `(清理后的麦克风帧, 原始扬声器帧, 时间戳)` 三元组 — [screenpipe core/aec.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/aec.rs)
- 分开采的另一个实际好处是**排错**：Thunder Kitty 的教训是"混在一起听着像能用"，其实系统声音全是零、对方的声音是麦克风从扬声器里漏录进来的；把扬声器静音后转写里只剩自己的声音才暴露问题 — [dev.to: 2,000 Buffers of Nothing](https://dev.to/nickdelv/2000-buffers-of-nothing-3i8)
- Recall.ai 把"系统声音与麦克风保持同步、处理延迟最小化"列为必须自己解决的问题，并指出戴耳机时没有回声，应用应检测输出设备类型来决定开不开 AEC — [Recall.ai](https://www.recall.ai/blog/how-to-get-access-to-system-audio)

### Inferences
- 对"会议数字人"，分两路的价值比普通记录工具更大：(1) 系统声音一路的每句话可以直接标成"线上的人"，不用靠声纹猜；(2) 麦克风一路只剩"房间里的人"，声纹库不被线上声音污染；(3) 数字人自己的 TTS 是已知信号，等于有第三路"干净参考"。
- 现有管线是"一路 16k PCM → silero VAD → SenseVoice"。最小改动是 Hyprnote 式：两路各跑一个独立的 `Ears` 实例（各自 VAD、各自断句），在事件层按时间戳合并，而不是 Meetily 式先混音——混音后 VAD 在"两边同时说话"时会把两个人并成一句，也没法区分来源。
- 两路来自不同时钟（麦克风硬件时钟 vs 输出设备时钟），长会议会漂移；如果只是"分别识别、按时间戳合并"，几十毫秒的漂移无所谓；只有要拿系统声音当 AEC 参考时才需要 Hyprnote/screenpipe 那种采样级对齐。

### Gaps
- Hyprnote 双声道送识别后，本地模型是否真的分声道解码、还是在识别器内部再混音，没有往下读到 STT 适配层，未核实。
- 没找到任何项目公布"分路识别 vs 混音识别"的准确率对比数据。

## 3. 回声消除：浏览器 AEC3 够不够；语音智能体项目怎么处理"自己听到自己"；可独立使用的开源 AEC；Voice Processing I/O 能否在 Electron 用上

### Takeaway
在 Electron 43（Chromium 150）里，`echoCancellation: true` 的参考信号已经是"Chromium 送往该输出设备的全部声音"（Chrome-wide AEC 默认开），所以数字人从同一个应用里播放的 TTS 原则上都能被消掉；真正的薄弱点是双讲（它在说、人插话）时 AEC3 会压低人声，以及刚开口头几秒滤波器尚未收敛。业界（Deepgram、LiveKit、Pipecat）的共识是：优先用离声源最近的平台 AEC，再在逻辑层加保险（开场热身期不接受打断、把识别结果和刚说的 TTS 文本比对后丢弃），而不是堆更猛的信号处理。

### Cited Findings

**A. Chromium / Electron 里的 AEC 现状（源码一手）**
- `kChromeWideEchoCancellation` 默认开启，注释："请求麦克风回声消除时，在 audio service 里把送往特定输出设备的所有播放混合起来并消除"；该能力在 Win/Mac/Linux 上编译 — [chromium 150.0.7871.212 media_switches.cc](https://github.com/chromium/chromium/blob/150.0.7871.212/media/base/media_switches.cc)；[chromium media_options.gni](https://github.com/chromium/chromium/blob/main/media/media_options.gni)
- `kSystemLoopbackAsAecReference` 在 Chromium 150 和 main 里都是默认开启，注释："用系统回环音频作参考信号，以便消除来自所有音频进程（不只是 Chrome）的回声"；mac 上要求 macOS ≥ 14.2（tap）；使用时会把采集信号人为延迟 `added_delay_ms`（默认 170 ms）以保证参考先到 — [chromium 150.0.7871.212 media_switches.cc](https://github.com/chromium/chromium/blob/150.0.7871.212/media/base/media_switches.cc)
- `kEnforceSystemEchoCancellation`（Mac/Win）默认**关闭**，打开后强制用系统回声消除；附带参数可让系统 AGC/NS 与 WebRTC 的 AGC/NS 串联；注释写明"系统 AGC/NS 从不脱离系统 AEC 单独开启"。强制系统 AEC 时 Chrome-wide AEC 自动停用 — [chromium main media_switches.cc](https://github.com/chromium/chromium/blob/main/media/base/media_switches.cc)
- 历史背景：Chrome 自 M66（2018）起就以实验形式支持 macOS 原生回声消除（macOS 10.12+ 自带），M68 加了 `echoCancellationType: 'system' | 'browser'` 约束 — [Chrome 开发者博客: macOS native echo cancellation](https://developer.chrome.com/blog/macos-native-echo-cancellation)；[More native echo cancellation](https://developer.chrome.com/blog/more-native-echo-cancellation/)
- 早年的已知坑：Chromium 不对 WebAudio 直接输出的声音做回声消除（Chromium issue 687574），绕法是把 WebAudio 接到 `MediaStreamDestination` 再经 `<audio>` 元素/本地 WebRTC 回环播放 — [dev.to: Echo cancellation with Web Audio API and Chromium](https://dev.to/focused_dot_io/echo-cancellation-with-web-audio-api-and-chromium-mh3)

**B. 语音智能体项目怎么处理"自己听到自己"**
- **Deepgram 官方指南**：语音智能体先用平台原生 AEC（浏览器 `echoCancellation: true`、iOS 用 Voice Processing I/O）；让智能体**先说一句开场白**，给 AEC 校准时间；服务端 AEC 属于高级做法，需要麦克风+扬声器双路且**零时钟偏差**，并建议只在参考信号超过阈值时才运行 AEC、用干湿混合而不是 100% 用 AEC 输出，且提醒激进的 AEC 会压掉用户声音、让打断更难；对"回声漏进来"的轻量办法是**把每条识别结果和智能体刚说的 TTS 文本比对，匹配就丢弃**；打断判定建议用"识别出至少 N 个词"而不是纯能量 VAD — [Deepgram: Audio Preprocessing & Barge-In](https://developers.deepgram.com/guides/deep-dives/audio-preprocessing-barge-in)
- **LiveKit Agents**：`AgentSession` 有 `aec_warmup_duration`（Python 默认 3.0 秒，JS 默认 3000 毫秒，可设为 None 关闭），热身期内由音频活动触发的打断被抑制 — [LiveKit agents-js AgentSessionOptions](https://docs.livekit.io/reference/agents-js/types/agents.voice.AgentSessionOptions.html)；社区反馈它是固定计时器、不跟随 `say()` 实际时长，开场白长时会在中途失效（单个用户报告，未被官方确认）— [LiveKit 社区帖](https://community.livekit.io/t/session-say-hangs-indefinitely-20s-when-using-gemini-realtimemodel-gemini-3-1-as-llm-together-with-google-beta-geminitts-as-tts-session-input-set-audio-enabled-aec-warmup-duration-do-not-reliably-block-user-interruption-in-this-configuration/1448)
- **Pipecat**：维护者的立场是回声消除不归 Pipecat 管——"WebRTC 下 Chrome/Safari 自带回声消除（Firefox 没有），电话听筒自带"，相关 issue 以"超出 Pipecat 能影响的范围"关闭 — [pipecat issue #1771](https://github.com/pipecat-ai/pipecat/issues/1771)；框架层的办法是打断策略和"机器人说话时静音用户输入"（`AlwaysUserMuteStrategy`），代价是失去真打断 — [Pipecat 文档: interruptions](https://docs.pipecat.ai/pipecat/fundamentals/interruptions)；1.0 之后有用户报告开场白漏进用户侧被转写两遍，讨论结论是静音必须发生在 STT 之前，流式 STT 已经收到的音频拦不住 — [pipecat issue #4383](https://github.com/pipecat-ai/pipecat/issues/4383)
- **TEN Framework**：官方文档只讲打断的 flush 链路和用 VAD 触发，没有 AEC 配置说明 — [Agora TEN Agent: interrupt handling](https://docs.agora.io/en/ten-agent/develop/interrupt-handling)

**C. 同类会议应用里的 AEC 实现**
- **screenpipe**：(1) 软件 AEC 用 `sonora`——WebRTC 音频处理模块的纯 Rust 实现（BSD-3）；配置为 16k 单声道、10 ms 帧、高通 + AEC3（transparent mode HMM）+ 降噪 VeryHigh + AGC2 自适应数字增益，每帧先 process render（扬声器）、设置估计延迟、再 process capture（麦克风）— [screenpipe core/aec.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/aec.rs)；[dignifiedquire/sonora](https://github.com/dignifiedquire/sonora)。(2) 另有 macOS **VoiceProcessingIO** 路径（自家 cpal fork 打了补丁），而且放在**子进程**里跑，理由是"CoreAudio 调用无法被取消，进程级所有权才能杀掉卡死的单元" — [screenpipe core/vpio_process.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/vpio_process.rs)。(3) VPIO 的实际毛病：流创建成功（"AEC initialized"）却一个样本都不出，在装了很多虚拟声卡 + AirPods 反复连断的机器上出现；对策是同一设备 120 秒内连续 3 次死亡就降级回普通 HAL 采集 — [screenpipe device/vpio_health.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/device/vpio_health.rs)
- **Hyprnote**：自带 `aec` crate，是内嵌的 ONNX 神经网络 AEC——两个 ONNX 会话串联、带循环状态、块长 512 / 帧移 128、有 128/256/512 三档规模，输入是麦克风和回放（lpb）两路 — [anarlog crates/aec/src/onnx/mod.rs](https://github.com/fastrepl/anarlog/blob/main/crates/aec/src/onnx/mod.rs)；[anarlog crates/aec/src/onnx/model.rs](https://github.com/fastrepl/anarlog/blob/main/crates/aec/src/onnx/model.rs)；AEC 开关挂在"输出设备变化"回调上，可在运行中启停 — [anarlog capture/stream.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/src/capture/stream.rs)
- **Meetily**：依赖里没有任何 AEC（只有 nnnoiseless、ebur128、silero）— [meetily Cargo.toml](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/Cargo.toml)

**D. 可独立使用的开源 AEC**
- **Python 里直接可用**：`livekit.rtc.apm.AudioProcessingModule`（WebRTC APM 的封装）——构造参数 `echo_cancellation / noise_suppression / high_pass_filter / auto_gain_control`；`process_reverse_stream()` 喂远端（扬声器）帧，`process_stream()` 原地处理近端（麦克风）帧，`set_stream_delay_ms()` 设延迟；帧必须恰好 10 ms — [LiveKit Python rtc.apm 参考](https://docs.livekit.io/reference/python/livekit/rtc/apm.html)
- **DTLN-aec**：预训练的实时神经网络 AEC（MIT，397 星，最后提交 2022-04）— [breizhn/DTLN-aec](https://github.com/breizhn/DTLN-aec)
- **sonora**：纯 Rust 的 WebRTC APM（AEC3 + NS + AGC2），BSD-3，2026-11 仍在更新 — [dignifiedquire/sonora](https://github.com/dignifiedquire/sonora)
- PyPI 上还有 `aec-audio-processing`（未核实其内容与维护状态）— [PyPI: aec-audio-processing](https://pypi.org/project/aec-audio-processing/)

### Inferences
- 本项目 `audio.js` 的播放链路是 WebAudio → `MediaStreamDestination` → `<audio>.srcObject`，正好是早年那个"WebAudio 不被 AEC 覆盖"问题的标准绕法；在 Chrome-wide AEC 默认开启的 Chromium 150 上，这层绕法大概率已非必需，但留着无害。
- Hyprnote 的 AEC 模型结构（双 ONNX、512/128、三档规模）与 DTLN-aec 的公开结构一致，推测就是 DTLN-aec 的移植；仓库里没找到明确署名，属推断。
- "数字人说话时还要听人插话"是 AEC 最难的双讲场景。可叠加的低成本保险，按业界做法排序：(1) 开口头 2–3 秒不接受打断（LiveKit 式热身）；(2) 打断判定要求"识别出实词"而不是 VAD 一响就停（Deepgram 建议）；(3) 把此刻的识别文本与正在播的 TTS 文本做相似度比对，像自己说的就丢（Deepgram 建议；本项目后台本来就知道每个 `clip_started/clip_ended` 的文本和时间，实现成本很低）；(4) 输出设备是耳机时可以关 AEC（Recall.ai 建议），避免 AEC 无谓地损伤人声。
- 想在 Electron 里用上 macOS Voice Processing I/O，有两条路：一是给 Chromium 加 `--enable-features=EnforceSystemEchoCancellation`（源码里存在、默认关）；二是像 screenpipe 那样在原生子进程里自己开 VPIO。screenpipe 的经验表明 VPIO 在复杂音频设备环境下不稳，需要健康检查和降级；且 VPIO 会连带启用系统的降噪和增益，对识别未必有利（见第 4 节）。
- 如果以后改成"系统声音走 tap 进 Python"，Python 侧可以用 `livekit.rtc.apm` 拿 TTS 的 PCM 当参考做第二道 AEC；但 Deepgram 明确提醒服务端 AEC 需要零时钟偏差，本机同一时钟下可行，仍需对齐播放延迟。

### Gaps
- `SystemLoopbackAsAecReference` 在 Electron 43 的 macOS 构建里实际是否生效、是否需要"系统音频录制"授权才启用、那 170 ms 的附加采集延迟是否真的加在了本项目的麦克风链路上：只看到了开关和注释，未读 audio service 的启用条件，**未核实，值得实测**（对打断延迟有直接影响）。
- `EnforceSystemEchoCancellation` 在 Electron 43 上打开后的实际效果（是否真的走 VPIO、MacBook 麦克风阵列的波束成形是否随之启用）未实测。
- 没找到 AEC3 在"扬声器播 TTS + 远场多人插话"场景下的公开量化评测（ERLE、双讲时人声损失对识别率的影响）。
- Chromium issue 687574 的当前状态未能直接查看。

## 4. 降噪/语音增强对识别准确率是帮助还是伤害；浏览器的 noiseSuppression / autoGainControl 开着好不好

### Takeaway
对 Whisper/Parakeet 这一代在带噪数据上训练的识别模型，**单通道降噪前处理在多项独立评测里都让识别变差**，根因是降噪引入的"人工痕迹"比残留噪声更伤识别；Deepgram 官方建议纯转写场景直接送原始音频。但降噪对 **VAD/断句/打断判定**是有帮助的。所以合理的结构是"两条支路"：降噪后的信号只喂 VAD 和打断判定，识别用原始（或只做了 AEC 的）信号。针对 SenseVoice 的专门评测没有找到。

### Cited Findings

**A. 降噪伤识别的依据**
- arXiv 2512.17562（2025-12）《When De-noising Hurts》：用 MetricGAN-plus-voicebank 做前处理，测 Whisper、Parakeet、Gemini Flash 2.0、Parrotlet-a 四个系统、500 条医疗语音、多种噪声条件；**全部 40 个配置里原始带噪音频的 semWER 都低于增强后的音频**，增强造成的 semWER 绝对增幅在 1.1% 到 46.6% 之间；作者认为现代 ASR 本身已有足够的噪声鲁棒性，降噪反而去掉了模型需要的声学特征（注：摘要写 9 种噪声条件，结果按 4×10=40 个配置统计，原文有出入）— [arXiv:2512.17562](https://arxiv.org/abs/2512.17562)
- arXiv 2603.04710（2026-03）：用 Meta 的 SAM-Audio 给 Whisper 做零样本前处理，听感质量提升但 WER/CER 一致变差，且 Whisper 模型越大退化越明显；其相关工作部分也引用了反例（CHiME-4 上某单通道时域降噪取得 30% 以上相对 WER 下降）— [arXiv:2603.04710](https://arxiv.org/html/2603.04710)
- Alcatel-Lucent Enterprise（ICAART 2024 论文的企业博客摘要，二手）：RNNoise 和 Asteroid 两种降噪配 Vosk、Whisper，结论是降噪可能对识别有负面影响、造成重要信息丢失 — [ALE: Surprising impact of noise reduction on ASR](https://www.al-enterprise.com/zh-cn/blog/noise-reduction-study-asr)
- 机理（NTT，arXiv 2404.14860，2024）：把增强误差分解为"自然的残留噪声"和"不自然的处理痕迹（artifact）"，分析表明**对识别特别有害的是 artifact**，残留噪声影响很小；并证明"observation adding"（把增强后信号与原始信号按比例加回去）能单调改善信号-痕迹比，从而显著改善识别 — [arXiv:2404.14860](https://arxiv.org/html/2404.14860v1)
- Deepgram 官方指南：纯转写（录音或流式）"建议完全跳过降噪，送未处理的音频以获得最佳准确率"；"很多做了 A/B 测试的客户发现去掉降噪后准确率提高"；降噪会削掉轻声说话者、带口音的语音和"是/不是"、人名这类短词；其浏览器示例代码把 `noiseSuppression` 设为 `false`；只有在语音智能体出现误打断时才考虑加降噪，且要保守、要 A/B — [Deepgram: Audio Preprocessing & Barge-In](https://developers.deepgram.com/guides/deep-dives/audio-preprocessing-barge-in)；[Deepgram 博客: The Noise Reduction Paradox（2025-07）](https://deepgram.com/learn/the-noise-reduction-paradox-why-it-may-hurt-speech-to-text-accuracy)
- 同类项目的实际选择：Meetily 集成了 RNNoise（nnnoiseless）但用编译期常量 `RNNOISE_APPLY_ENABLED = false` **默认关掉**，注释写"Whisper handles noise well" — [meetily audio/ffmpeg_mixer.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/ffmpeg_mixer.rs)；[meetily audio/pipeline.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/pipeline.rs)

**B. 反方向的说法（多为厂商文档，无公开基准）**
- OpenAI Realtime API 的 `input_audio_noise_reduction`：在音频进 VAD 和模型之前过滤，文档称"可以提高 VAD 和轮次检测的准确性（减少误报）并改善模型表现"；分 `near_field`（耳机等近讲）和 `far_field`（笔记本、会议室麦克风）两档 — [OpenAI SDK 类型文档](https://www.rubydoc.info/gems/openai/OpenAI/Models/Realtime/RealtimeSession/InputAudioNoiseReduction)
- LiveKit 文档称背景噪声会干扰轮次检测并降低转写质量，提供 Krisp 授权的 NC/BVC 模型；同时明确区分：**人声隔离（去掉非主说话人）最适合单人说话，多人说话和说话人分离场景应该用普通背景降噪** — [LiveKit: noise & echo cancellation](https://docs.livekit.io/transport/media/noise-cancellation)；[LiveKit: enhanced noise cancellation recipe](https://docs.livekit.io/recipes/enhanced-noise-cancellation)；也有用户报告开 BVC 后音质明显变差 — [LiveKit 社区帖](https://community.livekit.io/t/unexpected-audio-degradation-after-enabling-bvc-noise-cancellation-in-livekit-voice-agent/745)
- screenpipe 在 AEC 管线里把 WebRTC 降噪开到 VeryHigh 并开 AGC2，但仓库里另有专门的识别评测 crate（WER、DER 计算，LibriSpeech 夹具，"安静房间幽灵词"端到端测试），说明他们是带着评测做这个选择的；评测结果本身未公开在所读文件里 — [screenpipe core/aec.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/aec.rs)；[screenpipe-audio-eval](https://github.com/screenpipe/screenpipe/tree/main/crates/screenpipe-audio-eval)

**C. 可用的开源降噪实现**
- sherpa-onnx 内置语音增强：GTCRN（`gtcrn_simple`）和 DPDFNet（8k/16k/48k 三种变体，有离线和流式的 Python/C API，离线模式有"衰减上限"参数）；文档没有任何对识别率影响的说明 — [sherpa-onnx speech enhancement 文档](https://k2-fsa.github.io/sherpa/onnx/speech-enhancement/index.html)；DPDFNet 是在 DeepFilterNet2 上加双路径块的因果单通道模型 — [arXiv:2512.16420](https://arxiv.org/html/2512.16420v2)
- 其他：GTCRN 官方实现（MIT）— [Xiaobin-Rong/gtcrn](https://github.com/Xiaobin-Rong/gtcrn)；RNNoise（BSD-3）— [xiph/rnnoise](https://github.com/xiph/rnnoise)；DeepFilterNet — [Rikorose/DeepFilterNet](https://github.com/Rikorose/DeepFilterNet)

**D. 增益（AGC）**
- Meetily 和 Hyprnote 都**没用 WebRTC 式 AGC**，而是用 EBU R128 响度归一：目标 −23 LUFS、按累计响度缓慢调整增益、加 10 ms 前瞻的真峰值限幅（Hyprnote 限幅 −1 dBTP）；Meetily 麦克风链路顺序是 80 Hz 高通 →（可选 RNNoise）→ 响度归一，注释强调"先去噪再放大" — [anarlog audio-actual/src/norm.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/src/norm.rs)；[meetily audio/audio_processing.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/audio_processing.rs)；[meetily audio/pipeline.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/pipeline.rs)
- 一篇针对普通话识别的论文（Sensors 2022）主张增益控制策略选得不好会抬高错误率，并提出以减小这种损害为目标的增益策略（只看到摘要级信息，具体数字未核实）— [MDPI Sensors 22(8):3027](https://www.mdpi.com/1424-8220/22/8/3027)

### Inferences
- 浏览器的 `noiseSuppression: true` 属于"单通道、偏激进、为人耳优化"的降噪，按上面的证据链，对 SenseVoice 的识别**更可能是负面或中性**，而不是正面；但它对 silero VAD 少切出杂音段有帮助。本项目 `ears.py` 已经有"挡非人话"的一层，降噪的边际收益更小。
- 约束是三个开关不完全独立：Chromium 里关掉 NS/AGC 仍可保留 AEC（`echoCancellation: true, noiseSuppression: false, autoGainControl: false` 是合法组合，Deepgram 示例即如此）。所以最值得做的 A/B 是"会议室模式下只留 AEC，关 NS，AGC 单独再比一次"，用项目已有的真实会议录音回放、看字错率和断句数，而不是凭论文下结论。
- 远场小声说话者是 AGC 的受益者（见第 5 节），所以 AGC 不宜和 NS 一起一刀切关掉；更稳的替代是后台按句做响度归一（Meetily/Hyprnote 的做法），不依赖浏览器 AGC 的时变增益。
- 如果想保留降噪的好处又不伤识别，NTT 的"observation adding"是零成本手段：识别用 `α·降噪后 + (1−α)·原始`；sherpa-onnx 的 DPDFNet"衰减上限"参数是同一思路。
- 人声隔离类模型（Krisp BVC、macOS"语音突显"麦克风模式）会把"非主说话人"当噪声去掉，**对多人围坐的会议室是有害的**（LiveKit 文档的区分与此一致）。

### Gaps
- **没有找到任何针对 SenseVoice / FunASR 的"降噪前处理是否伤识别"的评测**（中文搜索只有泛泛的工程文章），也没有中文远场会议数据上的对比。现有证据全是英文 + Whisper/Parakeet 系，外推到 SenseVoice 是推断。
- 没有找到专门测"Chromium/WebRTC 的 NS 或 AGC 模块 → Whisper 类模型 WER"的公开实验。
- ALE 的 ICAART 2024 论文原文和 Sensors 2022 论文正文未能读取（代理拒连/403），数字未核实。
- "Deepgram 测了 40 个配置、WER 升高 1%–46%"的说法在二手文章里被归到 Deepgram 名下，实际出处是 arXiv 2512.17562，不是 Deepgram 的实验。

## 5. 远场/会议室拾音：多人围坐一个笔记本麦克风时的软件层改进手段

### Takeaway
单麦克风条件下软件能做的很有限：开源会议应用里**没有一家做了去混响或波束成形**，它们做的只是高通滤波 + 响度归一 + 限幅，以及"优先选内建麦克风、避开蓝牙麦克风"的设备策略。学术上远场系统的标准前处理是 WPE 去混响 + 波束成形，但后者需要多麦克风，前者在单通道下收益有限且会引入第 4 节所说的处理痕迹风险。

### Cited Findings
- 远场的损失量级：把头戴麦克风换成远场阵列录音，WER 相对上升约 75%；WPE 去混响 + 波束成形是多数先进远场系统的标准前处理 — [arXiv:2108.05520](https://arxiv.org/pdf/2108.05520)
- WPE 的开源实现：`nara_wpe`（MIT，numpy/TensorFlow，离线与在线版本）— [fgnt/nara_wpe](https://github.com/fgnt/nara_wpe)
- 增益对远场的作用（专利文献，证据等级低）：5 米远场下，固定麦克风增益 WER 13.46%，加为识别设计的 AGC 后 8.46%；并指出很多识别管线要么不做 AGC，要么沿用为 VoIP 设计的 AGC，目标不同 — [US10657983 Automatic gain control for speech recognition](https://patents.justia.com/patent/10657983)
- 同类项目实际做的：Meetily 麦克风链路 = 80 Hz 一阶高通 + EBU R128 归一（−23 LUFS）+ 前瞻限幅，对极小声音频设最小放大倍数并在 ±0.95 软限幅 — [meetily audio/audio_processing.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/audio_processing.rs)；Hyprnote 同为 −23 LUFS + −1 dB 真峰值限幅 — [anarlog audio-actual/src/norm.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/src/norm.rs)
- 设备策略：screenpipe 在选定的输入设备掉线需要顶替时，按名称启发式**优先内建麦克风**，避免抓到虚拟/聚合输入 — [screenpipe audio_manager/device_monitor.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/audio_manager/device_monitor.rs)
- OpenAI Realtime 把"笔记本或会议室麦克风"单列为 `far_field` 降噪档，说明厂商认为远场需要与近讲不同的处理 — [OpenAI SDK 类型文档](https://www.rubydoc.info/gems/openai/OpenAI/Models/Realtime/RealtimeSession/InputAudioNoiseReduction)

### Inferences
- 波束成形**需要多麦克风**：MacBook 内建的是三麦克风阵列，但 `getUserMedia` 交给应用的是系统处理后的单声道，应用层拿不到原始多通道，自己做不了波束成形；能间接用上阵列的只有系统级 Voice Processing（第 3 节的 `EnforceSystemEchoCancellation` 或原生 VPIO），效果未实测。
- 单麦克风下性价比最高的软件手段依次是：(1) 按句响度归一（把远处小声的人拉到和近处一样的电平再送识别，SenseVoice 对输入电平并非完全不敏感）；(2) VAD 阈值随底噪自适应，避免远处的人被切掉句首句尾；(3) 关掉人声隔离类处理；(4) 界面上提示"有人声音太小"（见第 7 节）。
- 最有效的其实是硬件：外接全向会议麦克风/扬声器一体机（自带阵列和 AEC），软件只需识别出这类设备后关掉自己的 AEC/NS，避免双重处理。
- 单通道 WPE 可以试，但应按第 4 节的方法做 A/B，并考虑与原始信号按比例混合。

### Gaps
- 没找到任何开源会议记录应用在单麦克风远场上做去混响的实现或评测。
- macOS 在 `getUserMedia` 路径上是否对内建麦克风阵列做了波束成形、"语音突显/宽谱"麦克风模式能否在 Electron 应用里被用户启用：未核实。
- SenseVoice 在远场中文会议（如 AliMeeting 远场条件）上加/不加前处理的对比数据未找到。

## 6. 录音工程：落盘格式与分块、断线重连与丢帧检测、AudioWorklet → WebSocket 的坑、蓝牙、设备热插拔

### Takeaway
同类项目都把音频落盘，且都按"随时可能崩"来设计：Meetily 每 30 秒写一个检查点文件、结束时无重编码拼接；Hyprnote 每秒 flush + fsync WAV，新版改为 60 秒一个 `.part` 分块、落稳后才改名发布，磁盘出问题时先在内存里攒着。采集侧的共同经验是"静默失败最多"——设备消失、权限被拒、蓝牙切协议、SCK 停回调都不报错，必须靠"多久没来数据/数据是不是全零"的看门狗发现，并用带退避的重建恢复。

### Cited Findings

**A. 落盘与崩溃恢复**
- **Meetily**：会议目录 `名称_日期/`，其下 `.checkpoints/`；`IncrementalAudioSaver` 每攒满 30 秒写一个 `audio_chunk_NNN.mp4`；结束时用 FFmpeg concat demuxer + copy（不重编码）合并成 `audio.mp4` 再清理检查点；崩溃后启动时扫描检查点目录按文件名排序合并恢复；只存混音 — [meetily audio/incremental_saver.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/incremental_saver.rs)；[meetily audio/audio_processing.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/audio_processing.rs)
- **Hyprnote（旧路径）**：录制中写 WAV（`audio.wav`，双路模式下另有 `audio_mic.wav`、`audio_spk.wav`），每 1000 ms flush；一开始就先 flush + `sync_all` + 同步目录，"采集可能在第一个样本前就卡住，磁盘上要留一个可读的文件头"；结束后编码成 `audio.mp3`，编码失败就保留 WAV；再次打开时若发现损坏的 WAV，先改名为 `recovery-<uuid>.wav` 保全再新建 — [anarlog recorder/disk.rs](https://github.com/fastrepl/anarlog/blob/main/crates/listener-core/src/actors/recorder/disk.rs)
- **Hyprnote（新路径）**：流式立体声 MP3 编码，60 秒一个分块；编码在写线程，落盘在独立的持久化线程；分块先写 `.part`，**fsync 之后才改名发布**，未发布的 `.part` 下次启动时恢复；存储不健康时编码后的字节留在内存（上限 64 MB），恢复后按序补写，"磁盘慢或满只会延迟保存而不是丢音频"；预留 256 MB 磁盘余量，每 5 秒检查一次存储；有明确的人话错误（"Disk is full: audio saving stopped"、"Audio buffer is full while storage is unavailable"）；支持"零保留"模式（转写确认后才删音频）— [anarlog recorder/chunks.rs](https://github.com/fastrepl/anarlog/blob/main/crates/listener-core/src/actors/recorder/chunks.rs)

**B. 采集看门狗、重连与丢帧检测**
- Hyprnote 采集恢复：5 秒收不到帧算超时（`FRAME_TIMEOUT`），三级重试延迟，连续健康 30 秒后重置重试计数；原生驱动调用"无法取消"，所以超时的那次调用要一直持有到它返回，避免叠加新的调用；自动重试用尽后可手动重试；**输出设备变化时主动重开扬声器采集** — [anarlog capture/recovery.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/src/capture/recovery.rs)
- Hyprnote 丢帧检测：`DropoutMonitor` 统计 5 秒窗口内麦克风被补零的比例，超过 15% 就打 `mic_dropouts_detected` 并向界面发 `MicDropouts { ratio }` 事件；注释区分了"启动时扬声器流领先导致的正常补零"和"之后的补零 = 麦克风卡住" — [anarlog source/pipeline.rs](https://github.com/fastrepl/anarlog/blob/main/crates/listener-core/src/actors/source/pipeline.rs)
- screenpipe 设备恢复：指数退避，瞬时错误（如 SCK 尚未初始化）上限 8 秒，永久错误（没有任何输入/输出设备）用更长上限以免刷日志；判断"在运行"不只看启用列表，还要求流句柄存活且未标记断开（"启动失败会留下名字但没有流，以前因此挡住了输出恢复"）— [screenpipe audio_manager/device_monitor.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/audio_manager/device_monitor.rs)
- Meetily 设备监控：macOS 上注册 Core Audio 属性监听（硬件设备列表变化）即时唤醒监控循环，其他平台轮询；产生"在用设备断开/重新连上/设备列表变化"事件；麦克风热切换后同时更新系统声音设备名，因为"AirPods 这类蓝牙设备往往既是麦克风又是扬声器，断开时两个条目都失效" — [meetily audio/device_monitor.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/device_monitor.rs)

**C. 蓝牙耳机（HFP）**
- Meetily 管线注释：管线按 48 kHz 设计，但蓝牙设备经常报告 8 kHz、16 kHz 或 44.1 kHz（点名 Sony WH-1000XM4）；不按设备实际采样率重采样的话"音频被加速 3 倍，VAD 失效"；所以用**持久的、带缓冲的重采样器**处理 320/512/1024 等不定长的块 — [meetily audio/pipeline.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/pipeline.rs)
- screenpipe：蓝牙设备在睡眠唤醒或应用切换时常抖动几秒，所以选定的输入设备消失后**等 20 秒**才启用替补，避免来回折腾；替补优先内建麦克风；原设备回来后撤掉替补 — [screenpipe audio_manager/device_monitor.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/audio_manager/device_monitor.rs)
- Hyprnote 的麦克风打开流程里有专门的"为采集准备蓝牙输入"步骤，并在采集期间一直持有该激活句柄，注释称否则"拆除时会把输入恢复并弄成静音" — [anarlog audio-actual/src/mic.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/src/mic.rs)
- Thunder Kitty 的经验：先启动麦克风引擎、再建聚合设备，让 AirPods 先协商好 HFP；聚合设备挂在内建输出上而不是"默认输出"，因为默认输出会在接入耳机或蓝牙切协议时变化 — [dev.to: 2,000 Buffers of Nothing](https://dev.to/nickdelv/2000-buffers-of-nothing-3i8)
- 一般性背景（非一手来源）：Mac 一打开蓝牙耳机的麦克风就从高音质的 A2DP 切到通话协议 HFP，变成 8 kHz（CVSD）或 16 kHz（mSBC）单声道，播放音质同时下降；常见建议是耳机只当输出、输入选内建麦克风 — [GIGAZINE 2023-12](https://gigazine.net/gsc_news/en/20231213-mac-bluetooth-sound-quality)

**D. AudioWorklet → WebSocket**
- Doist（Todoist 语音功能 Ramble，2025-12）：AudioWorklet 的 `process()` 每次约 128 个样本，太碎，攒到 2048 个样本（约 40–50 ms）再发；主线程重采样到 16 kHz、转 16 位整型后经 WebSocket 发送；会话结束时未满的那一块直接丢弃 — [Doist: Building Ramble #2](https://www.doist.dev/building-ramble-2-capturing-audio-in-real-time)
- 同文的 Electron 专属坑：浏览器因自动播放策略让 `AudioContext` 初始挂起，Electron 没有这个限制，context 一建就在跑，**在系统层保持一条活跃音频流，导致电脑不休眠**（靠用户反馈才发现）；修法是建完立刻 suspend，会话开始才 resume — [Doist: Building Ramble #2](https://www.doist.dev/building-ramble-2-capturing-audio-in-real-time)
- Electron 文档：系统声音权限缺失时得到的是 `ended` 状态的死音轨，JS 侧没有任何错误 — [Electron desktop-capturer.md](https://github.com/electron/electron/blob/v43.3.0/docs/api/desktop-capturer.md)

**E. Core Audio 原生调用的工程性质**
- screenpipe 和 Hyprnote 各自独立得出同一结论：CoreAudio/原生驱动调用**不能被异步运行时取消**，可能卡死；screenpipe 的解法是把 VPIO 放进子进程（启动超时 18 秒、8 秒收不到样本算死、Drop 时必杀必回收），Hyprnote 的解法是让卡住的调用一直被持有到返回、不叠加新调用 — [screenpipe core/vpio_process.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/vpio_process.rs)；[anarlog capture/recovery.rs](https://github.com/fastrepl/anarlog/blob/main/crates/audio-actual/src/capture/recovery.rs)

### Inferences
- 本项目已经做对的（读 `avatar/web/audio.js` 所见）：1.5 秒收不到麦克风包就判定断流并自愈；音轨 `ended` 事件触发重接；选定麦克风消失时会议室模式回退到默认设备、线上模式不回退；`backgroundThrottling: false`；`AudioContext({ sampleRate: 16000 })` 失败时回退默认采样率。与同类项目相比**缺的主要是原始音频落盘**——目前只存识别后的文字，识别错了无法事后重跑，也无法离线做第 4 节那些 A/B。
- 落盘建议沿用最简单可靠的组合：Python 后台把收到的 16k 单声道 PCM 按 30–60 秒一块写成 FLAC 或 WAV（16k/16bit 单声道 WAV 约 115 MB/小时，FLAC 约一半），每块写完 fsync 再改名；麦克风和系统声音各存一路；结束时不合并也行（按文件名排序即可回放）。Opus/MP3 更小但有损，会影响以后重跑识别做对比；Meetily、Hyprnote 选有损格式是因为它们面向"回听"，本项目的首要用途是"重识别/调参"，无损更合适。隐私上要对应现有的 `guarded` 边界，默认保留期和"是否录音"应可在设置里关。
- WebSocket 链路上值得加的一个小东西是**序号/采样计数**：现在的二进制帧是裸 PCM，后台无法区分"浏览器没发"和"发了但丢了/乱序"，也无法发现时钟漂移；每帧带一个累计采样数，后台就能像 Hyprnote 的 `DropoutMonitor` 那样统计缺口比例并上报。
- 蓝牙：用户一旦把 AirPods 选作麦克风，输入变成 8/16 kHz 窄带单声道，同时数字人的播放音质也掉；值得在设备选择处把蓝牙麦克风标出来并默认避开（screenpipe 的"优先内建麦克风"策略），而不是只在采样率上兼容。
- Doist 说的"AudioContext 让电脑不休眠"与本项目相关：`outCtx` 和 `micCtx` 在会议结束后是否 close/suspend 值得核对一遍（`stopMic` 的实现未读全，属提醒而非结论）。
- 如果以后引入原生 tap 子进程，screenpipe"放子进程 + 超时必杀"的做法可以直接照搬，Python 侧用 `subprocess` 读 stdout 天然具备这个隔离。

### Gaps
- 没找到 MediaRecorder 或 AudioWorklet 在 1–3 小时长会议上丢帧/漂移的公开实测数据；Chromium 里 `AudioContext({sampleRate: 16000})` 内置重采样器的质量与自己在 worklet 里重采样的对比也没有找到可靠来源。
- "macOS 上 Chrome 的多个 AudioContext 只能用同一采样率"这一说法只在搜索摘要里见到，未读原文，未核实。
- Meetily 检查点为什么选 mp4（AAC）而不是无损格式、对事后重转写质量有无影响：源码里没有解释。
- screenpipe 的落盘格式没有读到（`write_retry.rs` 未读）。

## 7. 音量/电平的界面反馈：电平表、「没声音」检测、麦克风被静音提示

### Takeaway
各家都有电平表，但做得更到位的是**把"采集不健康"当成一等事件**往界面推：Hyprnote 推"麦克风丢帧比例"，screenpipe 有独立的音频健康/设备事件通道并且专门处理"接口说正常但其实没声音"，Meetily 推设备断开/重连事件。没有找到哪家把"麦克风被硬件静音"检测做成了公开可见的功能；Recall.ai 明确说系统 API 不提供静音检测，要自己做。

### Cited Findings
- **Meetily**：前端有独立的 `AudioLevelMeter` 组件、`RecordingStatusBar`、`AudioBackendSelector`（让用户切 SCK/Core Audio 后端），后端有 `level_monitor.rs` / `simple_level_monitor.rs`，以及设备断开/重连事件 — [meetily frontend/src/components](https://github.com/Zackriya-Solutions/meetily/tree/main/frontend/src/components)；[meetily audio/level_monitor.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/level_monitor.rs)；[meetily audio/device_monitor.rs](https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/device_monitor.rs)
- **Hyprnote**：采集帧里带 `mic_muted` 标志，静音时麦克风一路用零替换但系统声音照常；`DropoutMonitor` 在 5 秒窗口内补零比例超 15% 时发 `SessionDataEvent::MicDropouts { ratio }` 给前端；另有 `audio-sync/level.rs` 和为波形显示预计算峰值的 `fs-sync-core/audio/peaks.rs` — [anarlog source/pipeline.rs](https://github.com/fastrepl/anarlog/blob/main/crates/listener-core/src/actors/source/pipeline.rs)；[anarlog 仓库目录](https://github.com/fastrepl/anarlog/tree/main/crates)
- **screenpipe**：桌面端有 `engine_events/audio_health.rs` 和 `engine_events/audio_device.rs` 两个事件模块；SCK 看门狗的注释直接点出问题——流死了但"`/health` 仍报告 ok"，所以健康判断要基于"实际有没有送来音频"而不是"流对象在不在" — [screenpipe engine_events](https://github.com/screenpipe/screenpipe/tree/main/apps/screenpipe-app-tauri/src-tauri/src/engine_events)；[screenpipe sck_output_watchdog.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/sck_output_watchdog.rs)
- screenpipe 对"没声音"的细分：输出（系统声音）静音是**故意不当故障**的，因为没东西在放是常态；只有"45 秒静音 + 可用显示器集合变了"才判定流死 — [screenpipe sck_output_watchdog.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/core/sck_output_watchdog.rs)
- 静默失败必须靠看数据内容发现：权限被拒时 tap 的回调照常触发但全是零，"应用应该检查缓冲区是否包含非零数据"；并建议**把扬声器静音后测一次**，确认系统声音确实是采到的而不是麦克风漏录的 — [dev.to: 2,000 Buffers of Nothing](https://dev.to/nickdelv/2000-buffers-of-nothing-3i8)
- Recall.ai：AVAudioEngine 和 ScreenCaptureKit 都不处理麦克风切换、静音检测和麦克风选择；不做静音检测的话，用户在会议软件里静音后仍会被录进去 — [Recall.ai](https://www.recall.ai/blog/how-to-get-access-to-system-audio)

### Inferences
- 本项目主窗口的原则是"只放它本人，状态用动作和颜色表达"。同类项目的电平表在这里对应的是已有的 `onMicLevel` 驱动的"在听"神态；缺的是**异常态**的表达，可以按同类项目的事件分三种，各给一个一眼能看出的神态而不是文字：(1) 麦克风一直是数字零或长时间低于底噪（被系统/硬件静音、权限没给、选错设备）；(2) 丢帧比例高（Hyprnote 式 5 秒窗口统计）；(3) 系统声音一路"应该有却全零"（权限缺失，Electron/tap 都不报错）。对应的接口字段也应暴露给 Agent（如 `mic.health = ok | silent | dropping | denied`）。
- "全零"与"很安静"要分开判：真实麦克风即使在安静房间也有底噪，采样值不会是严格的 0；连续几秒严格为 0 基本可以断定是静音开关、权限或死音轨。这是从 Thunder Kitty 和 Electron 文档的行为描述推出来的判据。
- 系统声音一路不能照搬麦克风的"没声音就报警"，要学 screenpipe：线上没人说话是常态，只在"输出设备/显示器变了之后一直没数据"时才重建并提示。
- "有人声音太小"（远场）可以用按说话人统计的句级电平做提示，这是同类项目都没做、但对"围坐一个笔记本"场景有用的反馈。

### Gaps
- 没有逐个运行这些应用看实际界面，以上是从源码结构和事件定义读出来的；"哪家做得好"缺少基于实际体验的比较。
- 没找到开源项目里检测"会议软件内静音状态"（Zoom/Teams 的静音按钮）的实现；screenpipe 用 `is_running_input` 判断会议进程是否在用麦克风，是最接近的做法，但它反映的是"设备是否打开"而不是"软件静音"。
- macOS 上从 `getUserMedia` 能否区分"硬件静音键/系统输入音量为 0"与"环境安静"：未核实，需要实测 `MediaStreamTrack.muted` 在这些情况下的表现。
