# 会议智能体与语音框架：开源竞品的听说交互设计（截至 2026-11）

> 说明：星数、许可证、最近提交时间均取自 GitHub API（2026-11-12 查询）。标「源码」的参数是直接读仓库 main 分支得到的默认值；标「未核实」的是只有二手来源或没查到的。

## 1. 开源会议机器人 / 会议智能体盘点（怎么取音频、能不能说话、多人下如何决定回应）

### Takeaway
真正「能入会、能开口、自托管、许可证宽松」的开源项目目前只有 joinly 一个，而且它的轮次控制很朴素（VAD 静音 0.6 秒 + 提示词判断该不该说）；其余要么只录不说（Vexa 开源版、MeetingBot、ScreenApp），要么只是音频管道、把「何时说」留给使用者（Attendee），要么依赖闭源托管 API（Meeting BaaS、Recall 示例）。所有入会机器人方案都靠平台侧信息（界面上的「当前说话人」或每人独立音轨）认人，没有一个做声纹——本机采集 + 声纹认人是委托方项目独有的难点，也是独有的能力。

### Cited Findings

**joinly（joinly-ai/joinly）——最接近的竞品**
- 571 星，MIT，最近提交 2026-09-01（两个多月没动，活跃度一般）；定位是「让 AI Agent 入会并参与」的 MCP 中间件，支持 Google Meet / Zoom / Teams — [GitHub](https://github.com/joinly-ai/joinly)
- 取音频方式：Docker 里跑无头 Chromium（Playwright）入会，用 PulseAudio 虚拟扬声器 / 虚拟麦克风收发音频（源码有 `virtual_speaker.py`、`virtual_microphone.py`、`pulse_server.py`、`virtual_display.py`）；镜像约 2.3GB — [README](https://github.com/joinly-ai/joinly#zap-quickstart)、[源码目录](https://github.com/joinly-ai/joinly/tree/main/joinly/providers/browser)
- 认人方式：拿到的是混音，没有每人独立音轨；靠各平台页面上的「当前说话人」（`platform_controller.active_speaker`）给音频块打说话人标签，再随转写片段带出 — [meeting_provider.py](https://github.com/joinly-ai/joinly/blob/main/joinly/providers/browser/meeting_provider.py)、[google_meet.py](https://github.com/joinly-ai/joinly/blob/main/joinly/providers/browser/platforms/google_meet.py)
- 识别与合成：默认本地 Whisper（CPU 用 `base`，CUDA 用 `distil-large-v3`）+ 本地 Kokoro TTS，可换 Deepgram / ElevenLabs；VAD 有 silero / webrtc / hybrid 三种实现 — [README](https://github.com/joinly-ai/joinly#providers)
- 断句参数（源码）：`utterance_tail_seconds = 0.6`（最后一次检测到人声后静音 0.6 秒算一句完）；`no_speech_event_delay = 0.4`（一句话持续 0.4 秒以上才清掉「没人说话」标志，也就是说打断它至少要说 0.4 秒）；最多并发 5 个识别任务 — [transcription/default.py](https://github.com/joinly-ai/joinly/blob/main/joinly/controllers/transcription/default.py)
- 多人下是否回应：没有模型，全靠提示词。群聊提示词规定「只在被点名、上下文明显在等它、它领域内的问题卡住了讨论、或用工具能替大家省时间时才说；有人话说到一半、大家讨论得正顺、自己的话没有明显价值时不说；有人开始跟它对话后可以一直接话，直到对方明显转走」；一对一提示词则是「每句都回」。另有 `name_trigger` 开关：转写里出现它名字才触发 — [prompts.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/prompts.py)、[client.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/client.py)
- 大脑如何表示「这轮不说」：每轮必须以 `end_turn` 工具结束；不调用 `speak_text` 直接 `end_turn` 就是沉默 — [prompts.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/prompts.py)、[agent.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/agent.py)
- 路线图里未完成项：「改进句末 / 轮次检测」「摄像头画面带状态更新」「会内人工批准机制」「接 Speech2Speech 模型」「参会者进出事件」 — [README Roadmap](https://github.com/joinly-ai/joinly#pencil2-roadmap)

**Vexa（Vexa-ai/vexa）——最活跃，但开源版现在不能说话**
- 2,976 星，Apache-2.0，2026-11-12 仍有提交；机器人入 Meet / Teams / Zoom（Jitsi 待实测），实时流出带说话人的转写（Whisper / faster-whisper，可自托管），「先出草稿再确认」 — [GitHub](https://github.com/Vexa-ai/vexa)
- 0.12 版状态表自述：实时转写 + 说话人归属已生产可用，但「归属不保证：拿不准时发空说话人而不是猜，重度抢话下约 4–7% 的行没有说话人」 — [README Status](https://github.com/Vexa-ai/vexa#%EF%B8%8F-status--roadmap)
- 说话能力：`POST /bots/{…}/speak`（往会里放 TTS）和会中改配置在开源栈里「尚未接通，返回 404」；WebSocket 转写多路复用标为「计划中（目前轮询）」 — [README v0.12 note](https://github.com/Vexa-ai/vexa)
- 定位已转向「会议采集 + 沙箱里的编码智能体整理知识库」：会中不跑自己的模型，「只有一个智能，就是你的 Agent」 — [README](https://github.com/Vexa-ai/vexa)

**Attendee（attendee-labs/attendee）——音频管道最全，但不是开源许可证**
- 799 星，2026-11-12 仍有提交；许可证是 Elastic License 2.0（禁止作为托管服务提供给第三方），GitHub 识别为 NOASSERTION — [LICENSE](https://github.com/attendee-labs/attendee/blob/main/LICENSE)
- 取音频：WebSocket 双向实时音频，可收混音或**每位参会者独立音轨**（`realtime_audio.per_participant`，带 `participant_uuid`），采样率 8k / 16k / 24k，16 位单声道 PCM base64；往回发 `realtime_audio.bot_output` 就是机器人开口 — [realtime_audio.md](https://github.com/attendee-labs/attendee/blob/main/docs/realtime_audio.md)
- 转写两条路：第三方识别（基于每人独立音轨，「参会者停顿几秒后把这段送去识别」，支持 Deepgram / OpenAI / Gladia / AssemblyAI / Sarvam / ElevenLabs / Kyutai）或直接抓平台自带字幕（免费、质量较低）；文档称两者都有「完美的说话人识别」 — [transcription.md](https://github.com/attendee-labs/attendee/blob/main/docs/transcription.md)
- 说话 / 形象：给一个网页地址，Attendee 在容器里打开它，把会议音频当作网页的「麦克风」输入，把网页的音视频输出作为机器人的摄像头或共享屏幕送进会议（1280x720）——带形象的语音智能体可以直接这样进会 — [voice_agents.md](https://github.com/attendee-labs/attendee/blob/main/docs/voice_agents.md)
- 何时说话：Attendee 自己不管，交给接进来的语音智能体（文档示例是 Deepgram Voice Agent API、OpenAI Realtime API） — [realtime_audio.md](https://github.com/attendee-labs/attendee/blob/main/docs/realtime_audio.md)
- README 提到 Zoom 的每人独立音轨「只有 C++ 版 SDK 才有」，这是它自建的原因之一 — [README](https://github.com/attendee-labs/attendee)

### Inferences
- 入会机器人路线的最大好处是「认人免费」：Attendee 有每人独立音轨，joinly / Vexa 用平台的当前说话人标记。代价是抢话时不准（Vexa 自报 4–7% 空说话人），以及要维护一套随平台改版而碎的浏览器自动化。委托方本机麦克风采集必须自己做声纹，但线下会议、任意会议软件都能用，这是差异化。
- 入会机器人天然没有「听到自己」的问题（平台不会把你自己的声音回送给你），所以这些项目在回声处理上几乎没有可借鉴的代码；这块要看语音框架（第 4 节）。
- joinly 的「该不该说」完全压在一次 LLM 调用上，且用 0.6 秒静音就触发——委托方已有的话语权状态机（在听 / 在想 / 想发言 / 在说）比它精细。可借鉴的是它的三条提示词规则写法，以及「有人开始跟它说话后保持接话，直到对方转走」这条粘性规则。
- 如果委托方将来想支持远程会议，Attendee 的「把一个网页当语音智能体送进会议」是成本最低的路：现有的 3D 形象网页几乎可以原样当摄像头画面；但要注意 ELv2 许可。

### Gaps
- joinly 的 `active_speaker` 具体怎么从页面取（DOM 轮询还是事件）没有细读；抢话时的准确率没有公开数据。
- Vexa 说话人归属的实现细节（文档说的「binder」）未读源码；旧版（0.10 之前）是否有可用的 speak 接口未核实。
- 没有找到开源的「数字分身替我开会」类项目（搜索无结果）；商业产品不在本笔记范围。
- Meetily、Anarlog、AIRI 只看了仓库描述，没读实现。

## 2. 轮次判断（什么时候算对方说完了）

### Takeaway
主流做法已经从「静音够久」变成「短静音触发 + 小模型判断这句话说没说完」。能在本机 CPU 跑、支持中文、许可证干净的首选是 Pipecat Smart Turn v3（8MB，CPU 12–95 毫秒），但中文是它公开数据里偏弱的语言（准确率 88.57%）。这些模型全是为一对一设计的，只回答「这个人说完没」，不回答「该不该我说」。

### Cited Findings

**纯 VAD 静音时长（基线）**
- joinly：静音 0.6 秒算说完 — [源码](https://github.com/joinly-ai/joinly/blob/main/joinly/controllers/transcription/default.py)
- Pipecat 不用模型时：VAD `stop_secs` 默认 0.2 秒 + `user_speech_timeout` 默认 0.6 秒，停顿后最短等 0.8 秒；另有 5 秒兜底 `user_turn_stop_timeout` — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-turn-strategies)
- LiveKit：`min_delay` 0.5 秒、`max_delay` 3.0 秒（配流式音频判轮模型时收紧到 0.3 / 2.5 秒）；Silero VAD 默认 `min_silence_duration` 0.55 秒 — [turn.py 源码](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)、[LiveKit 文档](https://docs.livekit.io/agents/build/turns/turn-detector/)
- LiveKit 的「动态」模式（`mode: "dynamic"`，默认关）：用指数滑动平均（`alpha` 0.9）学这位用户句间停顿有多长，在 min / max 之间自适应；还把「刚判完说完、对方马上又接着说」当作一次误判来学 — [endpointing.py 源码](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/endpointing.py)

**Pipecat Smart Turn（v3，当前 v3.2）**
- 原理：直接吃音频（16kHz 单声道，最多 8 秒，取当前这一轮的全部音频，不足在前面补零），看韵律和语调，不依赖转写；Whisper Tiny 编码器 + 线性分类头，约 800 万参数；VAD 检测到静音时才跑一次 — [GitHub](https://github.com/pipecat-ai/smart-turn)
- 体积与速度：CPU 版 int8 量化 8MB、GPU 版 fp32 32MB；CPU 推理 12.6 毫秒（AWS c7a.2xlarge）到 94.8 毫秒（t3.medium），v2（wav2vec2，约 400MB）同机要 450–6272 毫秒 — [Daily 博客](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)
- 中文：支持（23 种语言之一）；v3 测试集上中文 945 条，准确率 88.57%，误判说完 4.76%，漏判说完 6.67%；对比英语 94.31%、日语 96.76%、韩语 96.85% — [Daily 博客](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)
- 许可证 BSD-2-Clause，数据集、训练脚本、权重全开源；1,666 星，2026-11-09 有提交 — [GitHub](https://github.com/pipecat-ai/smart-turn)
- 在 Pipecat 里是默认的结束策略（`TurnAnalyzerUserTurnStopStrategy` + `LocalSmartTurnAnalyzerV3`） — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-turn-strategies)
- 整体耗时：一份行业指南给的数字是 Smart Turn 在普通云 vCPU 上约 30 毫秒，从用户停顿到做出判断总共约 250 毫秒 — [Voice AI & Voice Agents 指南](https://voiceaiandvoiceagents.com/)

**LiveKit turn detector**
- 现在分三档：音频模型 `v1`（跑在 LiveKit 云上，自托管超出每月开发额度要按次计费）、音频模型 `v1-mini`（本机 CPU 跑，免费，每份权重占 140–250MB 内存）、旧的文本模型 `MultilingualModel`（标为弃用，将在 SDK 2.0 移除） — [LiveKit 文档](https://docs.livekit.io/agents/build/turns/turn-detector/)
- 文本模型：基于 Qwen2.5-0.5B-Instruct，磁盘 396MB，内存不到 500MB，CPU 每轮约 50–160 毫秒；吃的是转写文本 + 对话上下文 — [LiveKit 文档](https://docs.livekit.io/agents/build/turns/turn-detector/)
- 中文：音频模型 14 种语言含中文；文本模型中文的真阳性率 99.3%、真阴性率 86.60%（英语 99.3% / 87.00%）。音频模型没有公布准确率表 — [LiveKit 文档](https://docs.livekit.io/agents/build/turns/turn-detector/)
- 许可证：文本模型和 `v1-mini` 用「LiveKit Model License」（不是 Apache） — [LiveKit 文档](https://docs.livekit.io/agents/build/turns/turn-detector/)
- 流式判轮事件里除了「说完的概率」还带一个 `backchannel_probability`：「在这个停顿处，智能体附和一声合不合适」（本机 mini 模型不给这个值） — [turn.py 源码](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)

**TEN Turn Detection**
- 原理：文本模型，基于 Qwen2.5-7B，把用户的话分成三类：finished（说完了，等回应）、unfinished（停顿但还要说）、wait（明确叫 AI 别说，如「闭嘴」） — [GitHub](https://github.com/TEN-framework/ten-turn-detection)
- 中文：支持中英双语；自家测试集上中文 finished 98.90%、unfinished 92.74%、wait 92%（对比的「Model B」中文 74.63% / 88.89%，未点名） — [GitHub](https://github.com/TEN-framework/ten-turn-detection)
- 许可证：「Apache 2.0 附加条件」——不得部署在终端用户设备上、不得用于与 Agora 竞争的产品 — [LICENSE](https://github.com/TEN-framework/ten-turn-detection/blob/main/LICENSE)
- 627 星，2026-11-04 有提交；同家的 TEN VAD 2,310 星 — [GitHub](https://github.com/TEN-framework/ten-vad)

**用大模型自己判断（省一个模型）**
- Pipecat 的 `FilterIncompleteUserTurnStrategies`：让对话用的 LLM 在每次回复开头输出一个标记——● 说完了；◐ 用户马上会接着说；○ 用户需要更多时间。后两种保持这一轮不结束，等超时后再让 LLM 主动把人带回来 — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-turn-strategies)
- 同一做法在行业指南里的参数：✓ 立刻回应，○ 等 5 秒，◐ 等 10 秒 — [Voice AI & Voice Agents 指南](https://voiceaiandvoiceagents.com/)

**FireRedChat（小红书）**
- 自带「紧凑的句末检测模型（英文和中文）」和个性化 VAD，建在 LiveKit Agents 的分支上；604 星，Apache-2.0，最近提交 2025-09-28（一年多没更新） — [GitHub](https://github.com/FireRedTeam/FireRedChat)

**多人会议下还适用吗**
- 2026 年 3 月的论文《Speak or Stay Silent》直接指出现有语音助手「把每个停顿都当成请它说话」，把多人场景的问题定义为「每个停顿处，说还是不说」；用 12 万多条标注对话测了 8 个 LLM，零样本提示下「一致地失败」，带推理过程的监督微调把平衡准确率最多提高 23 个百分点；结论是「看上下文决定接不接话不是自然涌现的能力，必须专门训练」 — [arXiv 2603.11409](https://arxiv.org/abs/2603.11409)
- 2025 年的一个基准发现 GPT-4o 在三人对话里判断「这话是对谁说的」只比瞎猜好一点 — [arXiv 2501.16643](https://arxiv.org/abs/2501.16643)（经搜索摘要转述，未读全文）
- 另一篇评测 LLM 在会议里做「对谁说 / 是否换人 / 下一个谁说」预测的论文称多模态 LLM 好于纯文本，但仍不及人 — arXiv 2606.17542（仅见搜索摘要，未核实）
- 专门做「是不是对我说的」的开源项目：SAA（attenlabs/saa-sdk，131 星，2026-11-03 有提交）在 VAD 和识别之间加一道闸，按句判断是否对设备说，自称旁人闲聊、背景媒体、智能体自己的回放都能挡掉；但模型是托管的（WebSocket 连它的云，要 API key），开源的只是 Apache-2.0 的薄客户端 — [GitHub](https://github.com/attenlabs/saa-sdk)
- 框架里最接近的现成件：Pipecat 的 `WakePhraseUserTurnStartStrategy`（听到唤醒词才开始一轮，之后 `timeout` 默认 10 秒内不用再喊）；joinly 的 `name_trigger`；TEN 的 wait 类 — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-turn-strategies)、[joinly client.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/client.py)

### Inferences
- 这些判轮模型在多人会议里只解决一半问题：它们能告诉你「张三这句说完了」，但会议里张三说完之后更可能是李四接。委托方的做法（状态机管时机、大脑可以回「静」）方向是对的，论文结论也支持「该不该说」要单独建模，不能指望通用 LLM 零样本做好。
- 对委托方最实际的增量：在现有 VAD 断句之后加 Smart Turn v3 做「这句话说没说完」的二次确认（8MB、ONNX、Mac CPU 上应在几十毫秒内），用来把断句静音阈值压短而不至于抢话。风险是中文准确率偏低（约每 15 句漏判一句说完），所以只应作为「可以提前开始想」的信号，不能作为唯一依据。
- LiveKit 的动态断句（学这位说话人的停顿习惯）实现很轻（一个滑动平均），委托方已经有声纹认人，可以做成「每位说话人一个停顿均值」，比 LiveKit 的每会话一个更细。
- TEN 的 wait 类（「等一下」「你先别说」）值得单独识别：委托方已有「能被叫停」，但可以检查是否覆盖了「说话前就被预先叫停」的情况。TEN 模型本身因为 7B 体量和「不得部署在终端设备」的许可条件，不适合直接用。
- 「有人开始跟它说话后 10 秒内不用再点名」（Pipecat 唤醒词超时、joinly 粘性规则）是多人场景里便宜又有效的指向判断，比训练模型现实。

### Gaps
- 没有找到任何判轮模型在多人会议音频上的公开准确率；所有数字都是一对一场景、各家自己的测试集，彼此不可比。
- LiveKit 音频判轮模型 `v1-mini` 的准确率、延迟、对中文的效果没有公开数据。
- Smart Turn v3.1 / v3.2 相对 v3 的中文准确率变化未查到。
- FireRedChat 句末检测模型的底座、体积、准确率，论文摘要里都没有，需读全文（[arXiv 2509.06502](https://arxiv.org/abs/2509.06502)）。
- 《Speak or Stay Silent》是否放出数据和模型未核实；论文仍在投稿中。

## 3. 打断（barge-in）：真打断与附和、截断与记账、误打断恢复

### Takeaway
最成熟的是 LiveKit：打断至少要 0.5 秒人声，被打断后先暂停而不是丢弃，2 秒内没有转写出来就判为误打断并接着说；它还有一个专门分辨「真打断 / 附和」的音频模型（精确率 86%、召回 100%，能挡掉 51% 的 VAD 误打断），但只在它的云上跑。开源可本机用的只有「最少时长 / 最少字数」这类规则。

### Cited Findings

**LiveKit Agents（源码默认值）**
- `min_duration` 0.5 秒：人声至少这么长才算打断；`min_words` 0：至少几个词才算（要有识别）；文档建议调高它来忽略「嗯」「好」 — [turn.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)、[调优文档](https://docs.livekit.io/agents/logic/turns/tuning.md)
- `false_interruption_timeout` 2.0 秒 + `resume_false_interruption` True：被打断后静默 2 秒且没有转写出来，判为误打断，接着把话说完；会发 `agent_false_interruption` 事件 — [turn.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)、[事件文档](https://docs.livekit.io/agents/build/events/)
- `backchannel_boundary` 默认 (1.0, 1.0)：智能体每次开口的头 1 秒不用自适应模型（交给 VAD），尾 1 秒内晚到的转写当作正常的用户发言而不是重叠 — [turn.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)、[自适应打断文档](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling.md)
- `discard_audio_if_uninterruptible` True：智能体在说且设为不可打断时，直接丢掉这段时间收到的音频 — [turn.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)
- `user_turn_limit`（默认关）：用户连着说太久（按累计词数或时长）而智能体一直没能开口时触发，计数器只在智能体真的出声后清零 — [turn.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)

**LiveKit 自适应打断模型（2026 年新增）**
- 音频编码器 + CNN，看波形形状、起音的强度和陡度、时长、韵律；VAD 检测到人声后运行，不等转写 — [LiveKit 博客](https://livekit.com/blog/adaptive-interruption-handling)
- 数字：触发打断所需音频中位数 216 毫秒；推理 30 毫秒以内；64% 的情况下比 VAD 更快认出真打断；重叠 500 毫秒时精确率 86%、召回率 100%；挡掉 51% 的 VAD 式打断 — [LiveKit 博客](https://livekit.com/blog/adaptive-interruption-handling)
- 语言：称多语言、能泛化到训练时没见过的语言，「某些情况下英语更好」 — [博客](https://livekit.com/blog/adaptive-interruption-handling)、[文档](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling.md)
- 只在 LiveKit 云的推理服务上跑；自托管要显式设 `mode: "adaptive"` 并用云凭证，本地开发每月 4 万次免费，超额或服务不可用时退回 VAD — [文档](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling.md)、[博客](https://livekit.com/blog/adaptive-interruption-handling)
- 客户端参数（源码）：每 25 毫秒一帧，连续 2 帧（50 毫秒）起判，每 0.1 秒判一次，最多看 3 秒音频（含 1 秒前缀） — [interruption.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/inference/interruption.py)
- 判为附和后的处理：有识别的管道只丢掉附和那一段转写；实时模型则整轮丢弃、清空缓冲、不回复 — [文档](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling.md)
- 社区有人问能否自托管这个模型，官方未给路线；有回复建议在 VAD 模式上自己叠一个附和分类器（非官方） — [LiveKit 社区](https://community.livekit.io/t/roadmap-for-adaptive-interruption-handling-in-self-hosted-livekit-workers/1172)

**Pipecat**
- 打断由「用户轮开始策略」触发，默认 VAD + 转写两个策略、先到先得，`enable_interruptions` 默认开 — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-turn-strategies)
- `MinWordsUserTurnStartStrategy`：机器人在说时要攒够 `min_words` 个词才算打断，不够的转写直接丢；机器人没在说时一个词就够 — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-turn-strategies)
- `KrispVivaIPUserTurnStartStrategy`：用 Krisp 的模型在机器人说话时过滤「uh-huh」类附和（阈值 0.5，20 毫秒帧），需要 Krisp 的闭源 SDK — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-turn-strategies)
- 可以分场景禁止打断：`AlwaysUserMuteStrategy`（机器人说话期间一律不听）、`FirstSpeechUserMuteStrategy` / `MuteUntilFirstBotCompleteUserMuteStrategy`（只保护开场白）、`FunctionCallUserMuteStrategy`（工具调用期间不听）；多个策略是「或」的关系 — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-mute-strategies)
- 被打断后空手而归的处理：`EmptyUserTurnConfig` 的 `interrupted_prompt` 默认会让机器人请用户再说一遍，`max_consecutive_recoveries` 默认 1 — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-turn-strategies)

**截断与「只说到哪」**
- 行业指南的原则：打断时停掉管道里所有处理并尽快停掉播放；上下文要对齐「用户实际听到的」而不是生成得比实时快的全文；用 TTS 的词级时间戳把已播出的文字记进上下文（Pipecat 自动做） — [Voice AI & Voice Agents 指南](https://voiceaiandvoiceagents.com/)
- LiveKit 有 `use_tts_aligned_transcript` 选项，用 TTS 对齐的转写同步 — [agent_session.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/agent_session.py)
- joinly 的做法（源码）：TTS 按语义切块（每块 15–50 词），最多预取 2 块；每写一小块音频前检查「是否有人在说」，有就抛 `SpeechInterruptedError`；已说内容按「每秒 2 个词」从已写出的字节数估算，记进会议转写时末尾加「...」，并把「Interrupted by detected speech」作为工具结果返回给 LLM，这一轮随即结束 — [speech/default.py](https://github.com/joinly-ai/joinly/blob/main/joinly/controllers/speech/default.py)、[agent.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/agent.py)
- Open-LLM-VTuber 的做法（源码）：前端把「用户实际听到的部分」（`heard_response`）回传，后端取消当前对话任务，调 `agent_engine.handle_interrupt(heard_response)`，并只把听到的部分存进历史 — [conversation_handler.py](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber/blob/main/src/open_llm_vtuber/conversations/conversation_handler.py)

**FireRedChat 的个性化 VAD**
- 用流式的个性化 VAD「抑制来自噪声和非主说话人的误打断」，只让主说话人能打断 — [arXiv 2509.06502](https://arxiv.org/abs/2509.06502)

### Inferences
- 委托方用「嗯」「对」判断对方在听，这和 LiveKit 的方向一致，而且委托方是在文本层做（识别后），LiveKit 是在音频层做（更快，约 216 毫秒）。本机没有可用的开源音频附和分类器，文本层 + 时长规则是现实选择；可以借的是三个参数化的想法：0.5 秒最短时长、开口头 1 秒不判附和、收尾 1 秒内的话算正常发言。
- 「先暂停、2 秒内没转写出字就接着说」比「一有声音就停并丢弃」体验好得多，委托方已有回声场景下的续说（`floor.py` 里对回声打断的恢复），可以推广到所有「打断后没识别出内容」的情况（咳嗽、椅子响、旁人小声说话）。
- 多人会议里「谁能打断它」是个独有问题：FireRedChat 的个性化 VAD（只有主说话人能打断）在一对一里是优点，在会议里反过来了——任何与会者都应能打断，但旁边的私下交谈不该。委托方有声纹和相似度分数，可以做「已登记与会者才算打断，未知声音需要更长时长」。
- joinly 按每秒 2 词估算已说内容太粗（中文更不适用）；委托方应以实际播出的音频时长对应到句子 / 字（按 TTS 返回的时间戳或按句切分播放）来记账。

### Gaps
- LiveKit 误打断恢复时是从断点续播还是整句重说，文档没写明，未读实现。
- Pipecat 被打断后上下文截断的具体实现和参数只见于指南的概述，未读源码。
- 没有找到开源、可本机运行的「附和 vs 打断」音频分类模型；中文附和词（嗯、对、是、好的）的专门处理没有公开做法。
- Krisp 的附和过滤模型准确率未查。

## 4. 自己听到自己（回声）

### Takeaway
框架层面基本不解决回声，而是假设设备 / 浏览器 / WebRTC 已经做了回声消除，然后加两道保险：开口后头几秒不接受打断（LiveKit 默认 3 秒），以及对「刚开口就被打断」做最短时长和音量平滑。本机用外放 + 麦克风、又不走 WebRTC 的应用，要自己接回声消除，没有现成的框架件。

### Cited Findings
- 行业指南：回声消除必须在设备端做（对延迟敏感）；电话栈、浏览器、WebRTC 移动 SDK 一般自带，自己写的 WebSocket 应用可能默认没有；为减少开口瞬间的回声误打断，用最短 VAD 起始段长度和音量指数平滑 — [Voice AI & Voice Agents 指南](https://voiceaiandvoiceagents.com/)
- LiveKit：`aec_warmup_duration` 默认 3.0 秒——智能体开始说话后这段时间忽略用户音频的打断，「防止回声消除还没准备好时被回声打断」；外呼电话默认关 — [agent_session.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/agent_session.py)
- LiveKit 在 VAD 和识别之前可以挂「人声隔离」（ai-coustics、Krisp BVC）压掉竞争人声；文档明确说人声隔离适合单人场景，多人房间应改用「背景噪声抑制」 — [调优文档](https://docs.livekit.io/agents/logic/turns/tuning.md)
- Pipecat 的音频滤镜只有降噪 / 人声隔离类（aic、koala、krisp_viva、rnnoise），没有回声消除滤镜 — [filters 目录](https://github.com/pipecat-ai/pipecat/tree/main/src/pipecat/audio/filters)
- Pipecat 的半双工开关：`AlwaysUserMuteStrategy` 在机器人说话期间屏蔽用户的音频和转写——等于说话时闭麦，代价是完全不能被打断 — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-mute-strategies)
- Open-LLM-VTuber 把「不戴耳机也能语音打断（AI 不会听到自己的声音）」列为特性 — [README](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber)；实现方式据一篇第三方评测说是利用浏览器麦克风采集管道自带的回声消除（未核实，未在仓库里找到对应代码） — [DEV Community 评测](https://dev.to/andrew-ooo/open-llm-vtuber-review-offline-ai-companion-with-live2d-327m)
- SAA 自称其指向检测能把「智能体自己的 TTS 回声」挡在识别之前（托管模型） — [GitHub](https://github.com/attenlabs/saa-sdk)
- joinly 等入会机器人用虚拟声卡收发，收到的是会议平台送来的远端音频 — [joinly 源码目录](https://github.com/joinly-ai/joinly/tree/main/joinly/providers/browser/devices)

### Inferences
- 各做法的代价对比：
  - 说话时闭麦（半双工）：最稳，但不能被打断，会议里不可接受（最多用于开场白或播报任务结果的头一句）。
  - 开口后前 N 秒不接受打断：便宜，LiveKit 用 3 秒；代价是这段时间真有人打断也不理。委托方已有类似处理（`floor.py` 注释「刚开口的头一小段不算打断」），可对照 3 秒这个量级检查自己的取值。
  - 系统 / 浏览器回声消除：效果最好，但只在走 WebRTC 采集时免费得到。委托方界面在 Electron 里，用 `getUserMedia({echoCancellation: true})` 采集就能用上 Chromium 的回声消除，前提是 TTS 也从同一个页面播出（回声消除要拿到参考信号）。
  - 用 TTS 文本过滤识别结果：委托方已经在做（`echo_score`，阈值 0.6）。调研的开源框架里没有一家做文本层回声过滤，这是委托方领先的地方；弱点是识别出来的回声文本常常残缺或被认错，所以应和声纹（「这段声音像不像它自己的 TTS 音色」）叠加。
  - 声纹排除：委托方有声纹系统，把 TTS 音色登记成一个「说话人」，认成它自己的片段直接丢，是独有的便宜手段；框架里没人这么做是因为它们没有声纹。
- 入会机器人没有声学回声（平台不回送自己的声音），所以 joinly、Vexa、Attendee 都没有相关代码；本机方案必须自己解决，这是本机采集路线的固有成本。

### Gaps
- Open-LLM-VTuber 的防自听实现未在源码里核实（前端在另一个仓库 Open-LLM-VTuber-Web，代码搜索没有结果）。
- 没有查 macOS 系统级回声消除（语音处理音频单元）在这类应用里的实际使用案例和效果数据。
- 没有找到「TTS 文本过滤回声」在任何开源框架里的实现或效果数据，无法对比委托方的阈值。

## 5. 延迟：从人说完到 AI 开口

### Takeaway
公开的分段预算里，最大的两块是「识别 + 断句」（约 300 毫秒）和大模型首字（350–650 毫秒）；整条链路约 1.2–1.3 秒，目标线是 1.5 秒以内。最有效的三个优化是：短静音 + 判轮模型（把断句从 0.8 秒压到约 0.25 秒）、预测性预生成（断句还没确认就开始想）、长任务先说一句再干。

### Cited Findings
- 分段预算（毫秒，云端管道、macOS 客户端）：麦克风输入 40、opus 编码 21、网络 10、包处理 2、抖动缓冲 40、解码 1、**转写与断句 300**、**LLM 首字 650**、句子聚合 20、**TTS 首包 120**、回程编码 21 + 包处理 2 + 网络 10 + 抖动缓冲 40 + 解码 1、扬声器输出 15，合计 1293；该页把 1,500 毫秒作为应当瞄准的端到端目标，并提到把模型放在同一 GPU 集群的演示能做到约 500 毫秒 — [Voice AI & Voice Agents 指南](https://voiceaiandvoiceagents.com/)
- 断句段：推荐组合是 200 毫秒的短 VAD 触发 + 原生音频的 Smart Turn + LLM 单字符标记；Smart Turn 约 30 毫秒，从停顿到判断共约 250 毫秒 — [同上](https://voiceaiandvoiceagents.com/)
- LiveKit 预生成（默认开）：最终转写一到就开始跑 LLM，不等这一轮被确认；`preemptive_tts` 默认关（开了更快但取消时浪费）；用户说话超过 10 秒不做预生成（「长的话更容易变」）；每轮最多重试 3 次；文档提醒「不一定总能降延迟」，要实测 — [turn.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/turn.py)、[调优文档](https://docs.livekit.io/agents/logic/turns/tuning.md)
- Pipecat 的 `EagerUserTurnStopStrategy`：按「提前的句末预测」先开始回应，`speculation_timeout` 默认 5 秒；用归一化匹配（忽略大小写和标点）判断最终转写是否和预测时一致，不一致就作废 — [Pipecat 文档](https://docs.pipecat.ai/server/utilities/turn-management/user-turn-strategies)
- joinly 的 TTS 流式：按语义切块，最多预取 2 块边合成边播；日志里记「STT utterance latency」 — [speech/default.py](https://github.com/joinly-ai/joinly/blob/main/joinly/controllers/speech/default.py)、[transcription/default.py](https://github.com/joinly-ai/joinly/blob/main/joinly/controllers/transcription/default.py)
- 填充语 / 先打招呼：
  - 行业指南：慢的函数调用，要么调用前先说一句，要么用看门狗定时器——只在调用确实拖久了才说 — [Voice AI & Voice Agents 指南](https://voiceaiandvoiceagents.com/)
  - LiveKit 有内部的 `_FillerScheduler`：长步骤期间，会话空闲满 `delay` 秒才说一句填充语，可按 `interval` 重复、`max_steps` 封顶；用户或智能体一开口就重新计时 — [filler_scheduler.py](https://github.com/livekit/agents/blob/main/livekit-agents/livekit/agents/voice/filler_scheduler.py)
  - joinly 用提示词强制：调外部工具前必须先用一句话口头说明要做什么，「绝不静默调用外部工具」；能并行就把 `speak_text` 和工具调用一起发 — [prompts.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/prompts.py)
- LiveKit 连续两句话之间的间隔 `min_consecutive_speech_delay` 默认 0，文档建议工具结果接在一句话后面时设 0.2–0.4 秒 — [调优文档](https://docs.livekit.io/agents/logic/turns/tuning.md)
- 各家公布的单点数字：Unmute 的 TTS 延迟单卡（L40S）约 750 毫秒、多卡约 450 毫秒 — [GitHub](https://github.com/kyutai-labs/unmute)；Moshi 理论延迟 160 毫秒、L4 GPU 上实际约 200 毫秒 — [GitHub](https://github.com/kyutai-labs/moshi)；LiveKit 文本判轮模型每轮 50–160 毫秒 — [LiveKit 文档](https://docs.livekit.io/agents/build/turns/turn-detector/)

### Inferences
- 会议场景对延迟的要求和一对一不同：一对一要越快越好；多人会议里接话太快反而像抢话，而且委托方本来就有「想发言 → 等空档」的状态。所以预算应分两段看——「想好要说什么」要快（预生成值得做），「开口」要等合适的空档（不需要压到几百毫秒）。
- 预生成和委托方的「在想」状态天然契合：一句话的最终识别结果出来就开始想，等状态机确认可以开口时答案已经有了；如果对方又接着说，按 Pipecat 的归一化匹配规则判断要不要作废重想。
- 委托方的后台任务汇报（`_reports` 欠账）对应 LiveKit 的填充语调度和 joinly 的「先说再干」。可借的细节是「空闲满 N 秒才说、有人开口就重新计时」，避免汇报插在别人说话中间。
- 本机链路没有网络和抖动缓冲那约 150 毫秒，但 SenseVoice 是整句识别而非流式，所以「转写与断句」这段是委托方最该量的地方。

### Gaps
- 没有找到任何开源会议智能体（joinly、Vexa、Attendee）公布的端到端分段延迟数据。
- 上面的预算表是云端管道；本机全离线链路（本机 ASR + 本机或远程 LLM + 本机 TTS）没有找到公开的分段数据。
- 行业指南的数字随版本有变化（本次读到的是 LLM 首字 650、合计 1293、目标 1,500；页面较长只读了前 10 万字符），引用时以原页为准。
- LiveKit 预生成实际能省多少，官方没给数字。

## 6. 状态表达：怎么让人知道它在听 / 在想 / 要说 / 在说

### Takeaway
语音框架只提供状态机和事件（LiveKit 是五态），怎么画留给前端；入会机器人几乎没有状态表达（joinly 把「摄像头画面带状态」列在未完成的路线图里），主要靠「干活前先口头说一声」。没有任何调研对象有「想发言」这个中间态——委托方的四态加琥珀色「想发言」是独有的设计。

### Cited Findings
- LiveKit 的智能体状态：`initializing`、`idle`、`listening`、`thinking`、`speaking`；用户状态：`speaking`、`listening`、`away`（默认 15 秒没回应）；状态通过参与者属性 `lk.agent.state` 暴露给前端 — [事件文档](https://docs.livekit.io/agents/build/events/)
- LiveKit 的可观测事件：`agent_state_changed`、`user_state_changed`、`user_input_transcribed`、`conversation_item_added`、`agent_false_interruption`、`overlapping_speech`、`speech_created`；博客提到新的调试面板能显示每次重叠被判成打断还是附和 — [事件文档](https://docs.livekit.io/agents/build/events/)、[博客](https://livekit.com/blog/adaptive-interruption-handling)
- joinly：客户端有 `on_status` 回调，状态只有 `llm_call` 和 `tool_call` 两种；会议里的可见表达靠提示词——工具调用前必须口头说明；路线图「摄像头画面带状态更新」未完成（源码里已有 `camera_feed.py`） — [agent.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/agent.py)、[README Roadmap](https://github.com/joinly-ai/joinly#pencil2-roadmap)
- joinly 的声音 / 文字分工规则：默认用说的；超过 5 句、含网址或很多数字、用户要求、或被要求静音时改发聊天消息；两者互补不重复（口头给摘要，聊天给细节） — [prompts.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/prompts.py)
- Open-LLM-VTuber：Live2D 表情由后端按情绪映射控制；可显示「AI 的内心想法」（表情、想法、动作，不念出来）；触摸反馈（点、拖）；桌宠模式（透明背景、置顶、鼠标穿透）；群聊时向所有客户端广播「Thinking...」文本和 `conversation-chain-start` 控制消息；用户的话识别出来后广播 `user-input-transcription` — [README](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber)、[group_conversation.py](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber/blob/main/src/open_llm_vtuber/conversations/group_conversation.py)
- Unmute：按 S 键打开双方字幕 — [GitHub](https://github.com/kyutai-labs/unmute)
- Attendee：语音智能体的网页画面直接作为机器人的摄像头或共享屏幕（二选一），形象状态由网页自己画 — [voice_agents.md](https://github.com/attendee-labs/attendee/blob/main/docs/voice_agents.md)
- Vexa：转写「先出草稿再确认」，实时流给界面 — [README](https://github.com/Vexa-ai/vexa)

### Inferences
- 调研对象的状态集合都是一对一的三态（听 / 想 / 说）。多人会议特有的「我有话要说、在等空档」没有人做，对应人类开会时的举手、前倾、吸气。委托方的「想发言 = 琥珀」正是这个空位；建议让这个状态尽量被会上的人注意到（动作幅度、声音提示），因为它的作用是让人给它让话。
- LiveKit 的 `away`（15 秒没人理）和 `agent_false_interruption` 这两个事件值得对照：前者对应「会议冷场」，后者可以让形象做一个「哦，没事，我接着说」的小动作，把误打断恢复变得可见。
- Open-LLM-VTuber 的「内心想法显示但不念出来」对会议数字人有用：在不打断会议的前提下表达「我注意到了 / 我在查」，对应委托方后台干活时绕头的小光球；可以考虑把一句话的想法放进设置窗口或字幕，而不是主窗口。
- joinly 的「口头 + 聊天互补」规则可以映射到委托方的「说话 + 资料板」：长内容、数字、链接上资料板，嘴上只说结论。

### Gaps
- 没有找到关于「AI 与会者如何表达想发言」的公开设计讨论或用户研究。
- Tavus / HeyGen 类商业形象产品及其开源替代的状态表达没有调研（Pipecat 有 tavus / heygen / lemonslice 传输，但只是把音频送去渲染口型）。
- LiveKit、Pipecat 的官方前端可视化组件（声波条、光球等）的具体设计没有查。
- 声音提示（开口前的提示音、吸气声）在这些项目里没有找到实现。

## 7. 全双工语音模型是否适合本机中文多人会议

### Takeaway
不适合。开源的原生全双工模型要么只有英语（Moshi），要么要独占高端显卡（7B 级），而且全部是按一对一训练的——它们的模型结构里只有「我」和「对方」两条音轨，没有「多个对方」「这句不是对我说的」「我选择不说」的概念。级联管道（识别 + 文本大脑 + 合成）加独立的话语权状态机，仍是多人会议唯一现实的方案。

### Cited Findings
- Moshi（kyutai-labs/moshi）：11,495 星，代码 Apache-2.0，最近提交 2026-09-09；7B 参数的时序 Transformer + Mimi 编解码器；理论延迟 160 毫秒，L4 GPU 上约 200 毫秒；有 MLX 版可在 Mac 上跑（int4 / int8 / bf16）— [GitHub](https://github.com/kyutai-labs/moshi)；模型卡标注语言为英语 — [Hugging Face 模型卡](https://huggingface.co/kyutai/moshika-mlx-bf16)（经搜索摘要转述）
- Unmute（kyutai-labs/unmute）：1,547 星，MIT，最近提交 2026-09-09；Kyutai 自己转向的级联方案——用低延迟的流式识别和合成把任意文本 LLM 包起来；识别服务要 2.5GB 显存、合成要 5.3GB 显存，需要 CUDA 12.1 — [GitHub](https://github.com/kyutai-labs/unmute)
- Sesame CSM（SesameAILabs/csm）：14,750 星，Apache-2.0，最近提交 2025-05-27（一年半没更新）；仓库自述是「对话式语音生成模型」，即会说话的合成模型，不是能听能判轮的全双工对话系统 — [GitHub](https://github.com/SesameAILabs/csm)
- FireRedChat：604 星，Apache-2.0，最近提交 2025-09-28；名字叫全双工，实际开源的是级联系统（FireRedASR + LLM + FireRedTTS）加个性化 VAD 和句末检测，建在 LiveKit 上；「上下文感知 TTS」「音频 LLM 服务」一直标着即将推出 — [GitHub](https://github.com/FireRedTeam/FireRedChat)
- Step-Audio 2（stepfun-ai/Step-Audio2）：1,526 星，Apache-2.0，最近提交 2026-03-16；端到端多模态大模型，面向语音理解和语音对话 — [GitHub](https://github.com/stepfun-ai/Step-Audio2)
- Kimi-Audio（MoonshotAI/Kimi-Audio）：4,751 星，GitHub 未识别出许可证，最近提交 2025-06-21（已停更）；音频理解、生成、对话的基础模型 — [GitHub](https://github.com/MoonshotAI/Kimi-Audio)
- FLM-Audio（北京智源，2025）：原生全双工、中英双语，约 7B 底座 — [arXiv 2509.02521](https://arxiv.org/abs/2509.02521)（经搜索摘要转述，未读全文）
- Ultravox（fixie-ai/ultravox）：4,588 星，MIT，最近提交 2025-12-12；直接吃音频的多模态 LLM（只出文字） — [GitHub](https://github.com/fixie-ai/ultravox)
- joinly 路线图里「支持 Speech2Speech 模型」仍未完成 — [README Roadmap](https://github.com/joinly-ai/joinly#pencil2-roadmap)
- LiveKit 的自适应打断与「自己管轮次」的实时模型（文档点名 Gemini Live API）不兼容，只支持把轮次交给客户端的实时模型 — [自适应打断文档](https://docs.livekit.io/agents/logic/turns/adaptive-interruption-handling.md)

### Inferences
- 判断依据有四条：(1) 中文——Moshi 不支持，支持中文的几个（Step-Audio 2、Kimi-Audio、FLM-Audio、FireRedChat）要么停更要么是 7B 级；(2) 本机——7B 音频模型实时跑需要独占一块好显卡，Mac 上 Moshi 的 MLX 量化版能跑但只有英语；(3) 多人——没有一个模型有说话人身份或「对谁说」的输入；(4) 可控性——委托方需要的「回静」「欠着的汇报」「派任务」「隐私边界」都靠文本大脑和状态机，端到端模型里这些无处安放。
- 连做出 Moshi 的 Kyutai 自己都推出了级联的 Unmute，FireRedChat 实际交付的也是级联——行业在可控性和可换大脑上向级联回摆。
- 值得从全双工研究里拿的不是模型而是思路：流式识别里顺带预测「停顿 / 说完」的概率（Unmute 的做法，细节未核实），以及个性化 VAD。

### Gaps
- Kyutai 识别 / 合成模型支持的语言、Unmute 的「语义 VAD」细节没有核实（官网页面抓取为空）。
- Step-Audio 2、Kimi-Audio、FLM-Audio 的硬件需求、是否真全双工、中文实时对话质量没有读文档核实，只有仓库描述和搜索摘要。
- 2026 年是否有新的开源中文全双工模型发布，一次搜索没有结果，不能排除遗漏。
- 没有任何全双工模型在多人场景的评测数据。

## 8. 会议记录对外开放：MCP / API 怎么设计

### Takeaway
两种思路：joinly 把「会议本身」做成 MCP 服务（工具 = 进会、说话、发消息；资源 = 可订阅的实时转写），Vexa 把「会议档案」做成 MCP 服务（工具 = 列会议、分页取转写、搜索、标注）。值得抄的细节是 joinly 的可订阅实时转写资源，和 Vexa 的分页游标 + 有副作用的工具必须声明「是人让我做的」。

### Cited Findings

**joinly（会中、实时）**
- 工具：`join_meeting`（链接、名字、可选密码）、`leave_meeting`、`speak_text`、`send_chat_message`、`mute_yourself`、`unmute_yourself`、`get_chat_history`、`get_participants`、`get_transcript`（可按最近几分钟过滤）、`get_video_snapshot`（看当前共享屏幕的截图） — [README Tools](https://github.com/joinly-ai/joinly#tools)
- 资源：`transcript://live`——实时转写 JSON，带时间戳和说话人，「可订阅，有新话语时实时推送」；客户端代码里还有 `transcript://live/segments`，区分「一句话说完」（utterance）和「一个片段」（segment）两种粒度的回调 — [README Resources](https://github.com/joinly-ai/joinly#resources)、[client.py](https://github.com/joinly-ai/joinly/blob/main/client/joinly_client/client.py)
- 自己说的话也写进同一份转写（角色标为 assistant），被打断的那段以「...」结尾 — [speech/default.py](https://github.com/joinly-ai/joinly/blob/main/joinly/controllers/speech/default.py)
- 安全：README 明确警告 MCP 服务「没有认证、接受客户端传来的配置，只适合本机单个可信客户端」，要绑定到 localhost，不要暴露到网络 — [README](https://github.com/joinly-ai/joinly#technologist-run-a-custom-client)
- 组合方式：joinly 客户端可以再挂别的 MCP 服务（配置文件里的 `mcpServers`），让会上的智能体直接用 GitHub、Notion、搜索等工具 — [README](https://github.com/joinly-ai/joinly#add-mcp-servers-to-the-client)

**Vexa（会后为主、带实时流）**
- MCP 是无状态的 FastAPI 服务，路由即工具，挂在 `/mcp`（可流式的 HTTP 传输）；每次调用把调用者的凭证原样转给网关，不直连数据库；认证用 `Authorization: Bearer <API key>` — [MCP README](https://github.com/Vexa-ai/vexa/blob/main/core/gateway/services/mcp/README.md)
- 内置工具：`parse_meeting_link`、`request_meeting_bot`、`update_bot_config`、`stop_bot`、`list_meetings`（limit / offset / status / platform / 元数据过滤）、`get_meeting`、`delete_meeting`、`get_meeting_participants`、`get_meeting_transcript`、`search_transcripts`、`annotate_meeting`、`speak_in_meeting`、`get_meeting_chat`、`list_recordings`、`report_issue`；另有各域自己声明的 `get_bot_status`、`get_recording` 等 — [MCP README](https://github.com/Vexa-ai/vexa/blob/main/core/gateway/services/mcp/README.md)
- 转写分页：`get_meeting_transcript` 按 `since_index` 翻页，每次最多 200 段，返回 `next_index`、`complete`，没取完时附一句 `note` 提示接着读 — [同上](https://github.com/Vexa-ai/vexa/blob/main/core/gateway/services/mcp/README.md)
- 有副作用的工具加人工确认位：`delete_meeting` 和 `speak_in_meeting` 必须带 `asked_by_a_human=true`，无人值守的工作进程会被拒 — [同上](https://github.com/Vexa-ai/vexa/blob/main/core/gateway/services/mcp/README.md)
- 设计原则（原文意译）：「一个列出来却被自己的门拒绝的工具，比不存在更糟——看不到工具的智能体还能想别的办法」；没声明的参数直接拒绝而不是悄悄丢弃 — [同上](https://github.com/Vexa-ai/vexa/blob/main/core/gateway/services/mcp/README.md)
- 自带 `report_issue` 工具：智能体遇到问题可以直接提工单，只带调用者密钥的加盐指纹，不带密钥本身 — [同上](https://github.com/Vexa-ai/vexa/blob/main/core/gateway/services/mcp/README.md)
- 实时：会中用 `GET /agent/meeting/stream` 取实时转写流；WebSocket 多路复用「计划中，目前轮询」；底层是 Redis 转写流 — [README](https://github.com/Vexa-ai/vexa)

**Attendee（REST + webhook + WebSocket，未见 MCP）**
- `GET /bots/<id>/transcript` 会中会后都能查（会中返回部分转写），每条带 `speaker_name`、`speaker_uuid`、时间戳；实时更新走 webhook；音频走 WebSocket — [README](https://github.com/attendee-labs/attendee)、[transcription.md](https://github.com/attendee-labs/attendee/blob/main/docs/transcription.md)

**Meeting BaaS meeting-mcp**
- MIT，30 星；工具覆盖建机器人、搜转写、管理录制，以及一大组日历工具（`listUpcomingMeetings`、`scheduleRecording`、`cancelRecording` 等）；有些工具有「把凭证直接放进参数」的变体（`...WithCredentials`） — [GitHub](https://github.com/Meeting-BaaS/meeting-mcp)

### Inferences
- 委托方现有的 `meetings` MCP（`list_meetings` / `read_meeting` / `search_meetings`）对应 Vexa 的档案式设计，已经覆盖了核心的三件事。可以补的：
  - 实时订阅：加一个类似 `transcript://live` 的可订阅资源，让别的 Agent 在会议进行中跟读，而不是只能会后读。
  - 分页游标：长会的 `read_meeting` 加 `since_index` / `next_index` / `complete`，避免一次吐出整场会把上下文撑爆；同时支持「只要纪要 / 只要整理稿 / 只要最近 N 分钟」。
  - 参会者与说话人：单独的 `get_participants`（委托方有声纹认出的名字和改名记录）。
  - 人工确认位：如果将来开放「让它在会上说一句」「派任务」这类有副作用的工具，照 Vexa 加 `asked_by_a_human` 之类的显式声明；会上的话是不可信输入，这一点和委托方现有的隐私边界一脉相承。
- joinly 把「说话」做成 MCP 工具，意味着任何 Agent 都能借它的嘴在会上发言；委托方的话语权由状态机管，如果开放类似工具，应让外部 Agent 的话进入「欠着的汇报」队列由状态机择机说，而不是直接出声。
- joinly「无认证、只绑本机」的警告对委托方同样适用：本机 MCP 默认只应监听回环地址；`guarded` 模式下对外暴露哪些会议要有同样的过滤。
- Vexa「凭证不进参数」和 Meeting BaaS「凭证直接放参数」是正反两个例子，后者不可取。

### Gaps
- joinly 的 `transcript://live` 推送的是全量还是增量、断线重连怎么补，没有读实现。
- Vexa 的 `search_transcripts` 是关键词还是语义检索、`annotate_meeting` 的数据结构未查。
- Attendee 是否有官方 MCP 未核实。
- 没有找到任何项目公开「会议纪要 / 待办」作为结构化资源的 MCP 设计（大多只给原始转写），委托方的「结论 / 待办 / 没定的事」结构在这点上没有参照物。
