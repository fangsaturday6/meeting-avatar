# 说话人分离与认人（开源方案、在线聚类技巧、会后修正、竞品交互）

> 调研时间：2026-11-12/13。数字全部来自各项目官方模型卡 / README / 源码，逐条附链接。
> **不同数据集、不同打分口径（有无 collar、是否计重叠、参考标注是否做过强制对齐）的 DER 不能横向比**，下文凡是并列的数字都注明了口径。
> 对照的项目现状（只读 `avatar/speakers.py`）：CAM++ 声纹 + 逐句在线归簇，阈值 0.55；不足 2 秒的短句只归属、不建新人、不更新质心；质心按 `min(count, 20)` 加权滑动更新；没有合并、没有会后重聚类、没有跨会议声纹库。

## 1. 主流开源方案及实测指标（DER、速度、流式、中文、许可证）

### Takeaway
2026 年下半年的格局变了：**端到端流式模型（NVIDIA Streaming Sortformer v2.1 → 9 月发布的 Nemotron-3-Diarization，8 人、0.32–1.04 秒延迟、训练集含 AISHELL-4 / AliMeeting）在中文会议上的流式 DER 已经明显好于「分段 + 声纹 + 聚类」的离线管线**（AliMeeting far：Nemotron-3 流式 10.8% vs pyannote community-1 离线 20.3%，口径不完全相同），而且 FluidAudio 已经把 Sortformer / LS-EEND / Nemotron 3 转成 CoreML 在 Apple Silicon 上跑。「逐块提声纹 + 在线聚类」这条路（diart、FluidAudio 的旧 DiarizerManager、本项目现状）被 FluidAudio 自己评价为「fragile」，流式 DER 是离线的 3–5 倍。

### Cited Findings

**pyannote.audio（3.1 / community-1）**
- community-1 许可证 CC-BY-4.0（需在 HF 上同意条款）；相对 3.1 的改进是「更好的说话人归属和计数」、新增 `exclusive_speaker_diarization`（同一时刻只给一位说话人，便于和转写时间戳对齐）、更易离线使用；模型卡没有提流式 — [pyannote/speaker-diarization-community-1](https://huggingface.co/pyannote/speaker-diarization-community-1)
- 官方 DER（无 collar、计重叠、全自动，表更新于 2025-09），3.1 / community-1 / precision-2（商用云端）：AISHELL-4 12.2 / 11.7 / 11.4；AliMeeting ch.1 24.5 / 20.3 / 15.2；AMI IHM 18.8 / 17.0 / 12.9；AMI SDM 22.7 / 19.9 / 15.6；MSDWild 25.4 / 22.8 / 17.3；RAMC 22.2 / 20.8 / 10.5；VoxConverse 11.2 / 11.2 / 8.5；DIHARD3 21.4 / 20.2 / 14.7 — [同上模型卡](https://huggingface.co/pyannote/speaker-diarization-community-1)
- PyTorch 版管线在 Mac 上的速度（FluidAudio 的旁证）：CPU 约 1.5–2 倍实时，`mps` 约 20–25 倍实时 — [FluidAudio Benchmarks.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)

**NVIDIA Streaming Sortformer v2 / v2.1 与 Nemotron-3-Diarization**
- Streaming Sortformer 用「按到场顺序的说话人缓存」（AOSC）记住之前出现过的人，端到端直接输出每帧每人的活动概率，天然处理重叠；**最多 4 人**，5 人以上明显变差；模型卡自述「主要用英语数据训练，非英语可能变差」，但训练集里有 AISHELL-4 和 AliMeeting；许可证是 NVIDIA Open Model License — [nvidia/diar_streaming_sortformer_4spk-v2.1](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2.1)
- v2 → v2.1 对会议场景提升很大（collar 0、计重叠、AMI/AliMeeting 用强制对齐后的参考标注）：1.04 秒延迟下 AliMeeting near 19.98 → 12.60，AliMeeting far 22.09 → 15.60，AMI IHM 25.11 → 16.67，AMI SDM 31.34 → 20.57 — [同上模型卡](https://huggingface.co/nvidia/diar_streaming_sortformer_4spk-v2.1)
- **Nemotron-3-Diarization**（2026-09-23 发布，1 亿参数，许可证 OpenMDW-1.1）：同一个权重支持流式和离线，**最多 8 人**，输入缓冲延迟最低 80 ms（推荐不低于 0.32 秒），训练数据约 1 万小时真实对话 + 8.26 万小时模拟混合，含普通话（AISHELL-4、AliMeeting）— [nvidia/nemotron-3-diarization](https://huggingface.co/nvidia/nemotron-3-diarization)
- Nemotron-3 对 Sortformer v2.1 的 DER（同一口径：计重叠、collar 0、强制对齐参考）：AliMeeting near 1.04s 延迟 6.59 vs 12.47；AliMeeting far 10.80 vs 15.58；AMI MHM 9.48 vs 16.36；AMI SDM 12.80 vs 21.73；NOTSOFAR1 单通道全集 12.77 vs 31.81；DIHARD III 全集 13.18 vs 19.60。0.32 秒延迟只比 1.04 秒差 0.4–1.8 个点（AliMeeting near 7.19、far 11.60）— [同上模型卡](https://huggingface.co/nvidia/nemotron-3-diarization)
- 速度（NVIDIA RTX PRO 5000，BF16，batch 1）：Nemotron-3 在 1.04 秒延迟下 38 倍实时（`torch.compile` 后 164 倍），0.32 秒延迟下 12.5 / 54 倍实时 — [同上模型卡](https://huggingface.co/nvidia/nemotron-3-diarization)
- 模型卡提醒：参考标注换了，DER 就变；它们用强制对齐标注是因为原始标注把段内静音也算成语音，会虚增漏检 — [同上模型卡](https://huggingface.co/nvidia/nemotron-3-diarization)

**FluidAudio（Apple Silicon / CoreML，Apache-2.0）**
- `Diarizer` 模块支持 pyannote、Sortformer、LS-EEND、Nemotron 3 四类；许可证 Apache 2.0 — [FluidAudio README](https://github.com/FluidInference/FluidAudio)
- 官方选型建议：**LS-EEND** 最多 10 人、抗重叠最好、可纯 CPU 跑，但更容易误报、不如 Sortformer 稳，100 ms 更新一次，约 900 ms 的暂定预测；**Sortformer** 说话人身份「极其稳定」，但限 4 人、会漏掉小声说话，480 ms 更新、560 ms 暂定；**DiarizerManager（旧的在线聚类）**「在背景噪声、背景对话、两人以上重叠、**短句**、声音相近的人上都吃力，最常见错误是标错人，低延迟流式表现差，而且是最耗算力的在线方案」；**离线 VBx 管线**是离线质量最好的 — [FluidAudio Diarization GettingStarted](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/GettingStarted.md)
- 离线管线（community-1 转 CoreML）：VoxConverse 平均 DER 15.07%、122 倍实时（默认步长）或 13.89%、65 倍实时（步长 0.1）——注意这是仓库自带打分器（collar 0.25、跳过重叠），和 pyannote 官方数不可比；AMI 16 场测试集同一打分器 10.6%、323 倍实时（M5 Pro）— [FluidAudio Benchmarks.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)
- 用 pyannote 口径（无 collar、计重叠）重测 AMI 头戴混音 16 场：CLI 默认 20.3%，步长 0.1 时 18.3%，对比 pyannote 官方 17.0%；「每时刻只留一位说话人」的输出会让漏检涨 6–8 个点、DER 涨 4–5 个点 — [同上](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)
- **在线聚类流式（同一 AMI SDM 16 场、同一打分器）**：10 秒块无重叠 38.2%，5 秒块无重叠 39.0%，3 秒块 1 秒重叠 53.3%，5 秒块 2 秒重叠 55.9%；错误主体是说话人混淆（29–50 个点），最差的会议里 4 个人被聚成 5–11 个；官方原话是这条路「对聚类非常脆弱」「只在必须实时时才用」— [同上](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)
- 端到端流式（同一打分器，AMI SDM）：Sortformer（NVIDIA 高延迟配置，M2）平均 31.7%，其中漏检 21.5、混淆 9.7，127 倍实时；Sortformer v2.1 高上下文流式 26.4%（混淆仅 2.4，835 倍实时）；LS-EEND（AMI 变体，500 ms 步长，M4 Max 纯 CPU）20.7%，混淆 5.9，74.5 倍实时 — [同上](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)
- Sortformer 的「离线整段」模式（每 30.72 秒窗口独立、无说话人缓存）在长会议上 DER 56.7%（混淆 32.7），而带缓存的流式只有 26.4%（混淆 2.4）——说明**跨窗口的说话人记忆才是关键** — [同上](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)

**diart（在线分离，MIT）**
- 做法：每 500 ms 更新一次的 5 秒滚动缓冲上跑 pyannote 分割（重叠感知），再做带「不可相连」约束的增量聚类；延迟可在 500 ms–5 s 间调；依赖 PyTorch + pyannote — [juanmc2005/diart](https://github.com/juanmc2005/diart)

**3D-Speaker（阿里达摩院，Apache-2.0）**
- 分离管线 = 可选的重叠检测 + VAD + 切段 + 声纹（CAM++ 等）+ 聚类；官方 DER：AISHELL-4 10.30%（pyannote 12.2%、DiariZen 11.7%），AliMeeting 19.73%（pyannote 24.4%、DiariZen 17.6%），AMI SDM 21.76%，VoxConverse 11.75%，两个内部中文会议集 18.91% / 12.78%（pyannote 22.37% / 17.86%）— [modelscope/3D-Speaker](https://github.com/modelscope/3D-Speaker)
- 还提供多模态（音视频）分离和基于文本语义的「说话人转换点检测」模型（中文 BERT）— [同上](https://github.com/modelscope/3D-Speaker)

**senko（3D-Speaker 管线的提速版）**
- VAD（pyannote segmentation-3.0 或 Silero）+ Fbank + CAM++ 批量推理 + 聚类（谱聚类或 UMAP+HDBSCAN）；Mac 上 VAD 和声纹走 CoreML；**Apple M3 上 1 小时音频 7.7 秒**；最好成绩 VoxConverse 13.5%、AISHELL-4 13.3%、AMI-IHM 26.5%；声纹模型是中英混合训练，所以中英文效果最好；**不输出重叠段**（同一时刻只报一位）；只做离线 — [narcotic-sh/senko](https://github.com/narcotic-sh/senko)

**DiariZen（BUT，WavLM + pyannote 框架）**
- 官方 DER（无 collar，各数据集同一套聚类超参）：Large-s80-v2 在 AISHELL-4 10.1、AliMeeting far 10.8、AMI-SDM 13.9、RAMC 11.0、VoxConverse 9.1；同表 pyannote 3.1 为 12.2 / 24.4 / 22.4 / 22.2 / 11.3 — [BUTSpeechFIT/DiariZen](https://github.com/BUTSpeechFIT/DiariZen)
- **模型权重是 CC BY-NC 4.0（仅限非商用）**，代码 MIT；安装依赖 PyTorch（README 给的是 CUDA 版）— [同上](https://github.com/BUTSpeechFIT/DiariZen)

**sherpa-onnx**
- 离线分离 = pyannote segmentation-3.0（ONNX）+ 任选一个声纹模型 + 聚类；示例参数：`num_clusters=-1` 时用 `cluster_threshold=0.5`（越小人越多），`min_duration_on=0.3`、`min_duration_off=0.5`，分割窗口步长比 0.1；示例里配的是 3D-Speaker ERes2Net-base 中文模型，并附了一段 4 人中文测试音频 — [offline-speaker-diarization.py](https://github.com/k2-fsa/sherpa-onnx/blob/master/python-api-examples/offline-speaker-diarization.py)
- 分割模型发布页只有 pyannote-segmentation-3-0（7 MB）和 Rev.ai 的 reverb-diarization v1（10.9 MB）/ v2（254 MB）— [speaker-segmentation-models](https://github.com/k2-fsa/sherpa-onnx/releases/tag/speaker-segmentation-models)

**FunASR**
- `AutoModel(model=..., vad_model="fsmn-vad", spk_model="cam++")`：CAM++ 提每个 VAD 段的声纹，`AutoModel` 对整段录音聚类后给匿名编号；README 明说编号「只在一段录音内有效，不是注册说话人识别」；1.4.19 起自动聚类时强制执行 `max_speakers`；另接入第三方 MOSS-Transcribe-Diarize（离线，转写+时间戳+匿名说话人一体）— [modelscope/FunASR](https://github.com/modelscope/FunASR)

**WhisperX**
- 分离直接调 pyannote（现在默认 community-1），再用 `assign_word_speakers` 按时间把词归给说话人；可传 `min_speakers` / `max_speakers`；README 的局限一节原话：「重叠语音处理得不好」「分离远谈不上完美」；纯离线 — [m-bain/whisperX](https://github.com/m-bain/whisperX)

### Inferences
- 对「中文、本机、实时、≤8 人」这个需求，目前指标最好的开源流式方案是 Nemotron-3-Diarization（或它的前身 Sortformer v2.1），而且 FluidAudio 已有 CoreML 版本。它的输出是「每帧每个槽位的活动概率」，不是声纹——所以它解决的是「会内谁在说」，**不解决跨会议认人**；跨会议仍要另提声纹（见第 6 节）。
- 如果坚持不引入 Swift/CoreML 依赖、留在 sherpa-onnx 生态，能做的是「在线归簇只当临时结果 + 会后用 pyannote 分割 + 全局聚类重算」（见第 4 节）。
- FluidAudio 的流式聚类数字（38–56%）和本项目的做法不完全一样（它按固定时长切块，本项目按 VAD 整句），但错误形态相同：主要是说话人混淆和「4 个人聚成 5–11 个」。

### Gaps
- NeMo MSDD（多尺度分离解码器）的当前指标和维护状态本次没有查到一手资料，未核实。
- Nemotron-3 在 Apple Silicon（CoreML）上的实测速度和 DER：FluidAudio README 列了支持，但 Benchmarks.md 里本次只读到 Sortformer 和 LS-EEND 的表，Nemotron 3 的 Mac 数字未核实。
- sherpa-onnx 是否已内置 Sortformer / Nemotron 类流式分离：发布页没有相应模型，未核实是否有其它入口。
- diart 论文里各延迟档位的 DER 具体数字本次未取。
- pyannote community-1 之后是否有更新的开源版本：模型卡表格停在 2025-09，未见后续开源版本。

## 2. 嵌入模型选型（短语音 1–3 秒、中文）

### Takeaway
公开的短语音对比里，**ERes2NetV2 是专门为短语音做的，2 秒 EER 比 ECAPA-TDNN、ResNet34 低约 25–30%**；CAM++ 在长语音和 CN-Celeb 上与它接近但更轻。sherpa-onnx 模型库里中文可直接用的有 CAM++（中文通用 / 中英增强版）、ERes2NetV2 中文通用、ERes2Net 系列、WeSpeaker CN-Celeb ResNet34。**没有任何公开表格给出 1 秒的 EER**，1–2 秒本来就是所有模型的不稳定区。

### Cited Findings
- ERes2NetV2 论文表 3（VoxCeleb1，注册用整句、测试句截成 3 秒 / 2 秒，全部在 3D-Speaker 工具包内复现）：VoxCeleb1-O 上 3 秒 / 2 秒 EER——ERes2NetV2 0.98% / 1.48%，ECAPA-TDNN 1.27% / 1.95%，ResNet34 1.47% / 2.12%，Res2Net 1.98% / 2.73%，旧版 ERes2Net 1.89% / 3.28%；VoxCeleb1-H 上 ERes2NetV2 2.06% / 2.98%，ECAPA-TDNN 2.59% / 3.71% — [ERes2NetV2 论文](https://arxiv.org/html/2406.02167v1)
- 同一论文整句成绩：ERes2NetV2（17.8M 参数、12.6G FLOPs）VoxCeleb1-O 0.61%；可见从整句到 2 秒，EER 涨到约 2.4 倍 — [同上](https://arxiv.org/html/2406.02167v1)
- 3D-Speaker 官方汇总（整句）：CAM++（7.2M）VoxCeleb1-O 0.65% / CN-Celeb 6.78%；ERes2NetV2（17.8M）0.61% / 6.14%；ERes2Net-large（22.46M）0.52% / 6.17%；ECAPA-TDNN（20.8M）0.86% / 8.01%；ResNet34（6.34M）1.05% / 6.92% — [modelscope/3D-Speaker](https://github.com/modelscope/3D-Speaker)
- CAM++ 原论文：VoxCeleb-O 0.73%、CN-Celeb 6.78%，参数比 ECAPA-TDNN 少 51%、EER 低 18% — [CAM++ 论文](https://arxiv.org/pdf/2303.00332)
- WeSpeaker 官方 CN-Celeb 成绩（无打分归一化 → 加 AS-Norm）：ResNet34 7.134% → 6.747%；ResNet221 5.965% → 5.708%；ECAPA-TDNN-c512 8.313% → 7.644%；ECAPA-TDNN-c1024 7.879% → 7.412% — [wespeaker cnceleb README](https://github.com/wenet-e2e/wespeaker/blob/master/examples/cnceleb/v2/README.md)
- WeSpeaker 官方 VoxCeleb1-O（无 LM、无 AS-Norm）：ResNet34 0.867%，CAM++ 0.803%，ECAPA-c1024 0.856%，ResNet221 0.569%，ResNet293 0.595% — [wespeaker voxceleb README](https://github.com/wenet-e2e/wespeaker/blob/master/examples/voxceleb/v2/README.md)
- WeSpeaker 说明：带 `LM` 后缀的模型做过 large-margin 微调，「在长音频（如 >3 秒）上更好」——反过来说，短句场景不一定该选 LM 版 — [wespeaker pretrained.md](https://github.com/wenet-e2e/wespeaker/blob/master/docs/pretrained.md)
- sherpa-onnx 声纹模型发布页可直接下载的模型：`3dspeaker_speech_campplus_sv_zh-cn_16k-common`（28.3 MB）、`3dspeaker_speech_campplus_sv_zh_en_16k-common_advanced`（28.3 MB）、`3dspeaker_speech_eres2netv2_sv_zh-cn_16k-common`（71.4 MB）、`3dspeaker_speech_eres2net_base_200k_sv_zh-cn_16k-common`（39.6 MB）、`3dspeaker_speech_eres2net_large_sv_zh-cn_3dspeaker_16k`（116.1 MB）、`3dspeaker_speech_eres2net_sv_zh-cn_16k-common`（220.6 MB）、`wespeaker_zh_cnceleb_resnet34` / `_LM`（各 26.5 MB）、`wespeaker_en_voxceleb_*`（ResNet34/152/221/293、CAM++）、`nemo_en_titanet_large`（101.4 MB）/ `titanet_small`（40.3 MB）/ `speakernet` — [speaker-recongition-models 发布页](https://github.com/k2-fsa/sherpa-onnx/releases/tag/speaker-recongition-models)
- 3D-Speaker 的「zh-cn 16k-common」系列是在约 20 万说话人的中文数据上训练的（CAM++、ERes2Net、ERes2NetV2 都有这一版）— [modelscope/3D-Speaker](https://github.com/modelscope/3D-Speaker)
- FluidAudio 对 CAM++（中文通用版）的实测：AMI 头戴混音里 3–8 秒的单人片段，同一场会内 EER 2.85%，跨会议 3.55%；AISHELL-1（干净朗读普通话）EER 0.48%，同人平均余弦 0.805、不同人平均 0.256；**送入前做「整句均值归一」把会内 EER 从 4.67% 降到 3.07%** — [FluidAudio Benchmarks.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)
- 各家对「多短算太短」的工程取值：FluidAudio 建新人至少 1.0 秒、更新声纹至少 2.0 秒；OpenWhispr 丢弃 <0.8 秒的段、攒够 1.6 秒才做实时认人；screenpipe 把超过 2 秒的段切成 ≤2 秒再提声纹、不足 0.1 秒（1600 采样点）的补零；Speakr 要求一个标签累计 ≥15 秒语音才进声纹库或自动贴名 — [FluidAudio SpeakerManager.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/SpeakerManager.md)；[OpenWhispr 博客](https://openwhispr.com/blog/local-speaker-diarization)；[screenpipe segment.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/speaker/segment.rs)；[Speakr voice_profiles.py](https://github.com/murtaza-nasir/speakr/blob/master/src/services/voice_profiles.py)

### Inferences
- 项目注释里写的「一两秒的短句和本人长句相似度可能只有 0.46」和公开数据一致：最好的模型在 2 秒时 EER 也是整句的 2.4 倍，没有模型能让 1–2 秒的单句声纹可靠。换成 ERes2NetV2 中文通用版（sherpa-onnx 直接可用，71 MB）值得做一次 A/B，但预期是「短句好一截」而不是「短句问题消失」；真正的解法在第 3 节的决策策略上。
- 注意换声纹模型后阈值要重标：不同模型的余弦分布不同（screenpipe 用 0.35，OpenWhispr 0.55/0.70，FluidAudio 用余弦距离 0.65，本项目 0.55），不能照搬别人的数。

### Gaps
- CAM++ 在 2 秒 / 3 秒截断下的 EER：ERes2NetV2 论文表 3 没有列 CAM++，没找到同口径数字。
- TitaNet 的短语音和中文 EER：未取到一手数字（sherpa-onnx 里的 TitaNet 是英文模型，中文表现未核实）。
- 任何模型在 1 秒语音上的公开 EER：没找到。
- 中文**会议远场**条件下各声纹模型的 EER 对比：没找到（3D-Speaker 数据集上的数字是多设备/多距离，但不是会议）。

## 3. 在线增量聚类的工程技巧

### Takeaway
各家实现高度趋同，可以归成一张清单：**双阈值（归属阈值松、更新阈值严）+ 时长门槛（建新人和更新质心各一个）+ 每人保留多份样例而不只是一个质心 + 人数上限且满员后强制并入最近的人 + 同一块里的两个本地说话人不许并成一个（不可相连约束）+ 定期找可合并的簇对**。本项目已有「短句不建新人、不更新质心」，缺的是更新用的更严阈值、多样例、人数上限、合并。

### Cited Findings

**diart 的增量聚类（源码逐行核对）**
- 三个参数：`tau_active`（本地说话人在这一块里的最大活动概率 ≥ 它才算「在说话」）、`rho_update`（本地说话人在这一块里的**平均活动占比** ≥ 它，才算「说得够长」，才允许更新质心或建新质心）、`delta_new`（余弦距离，和所有质心的距离都大于它才建新质心）；另有 `max_speakers`（默认 20）— [diart clustering.py](https://github.com/juanmc2005/diart/blob/main/src/diart/blocks/clustering.py)
- 流程：算本地说话人 × 全局质心的距离矩阵 → 屏蔽不活跃的本地说话人和未启用的质心 → 做一次最优一对一指派（`scipy.optimize.linear_sum_assignment`，即匈牙利算法）→ 超过 `delta_new` 的指派作废 → 没着落的本地说话人：还有空位且说得够长就建新质心；否则**按距离从近到远找一个本轮还没被别人占用的已有质心硬塞进去** → 只有「不是硬塞的、且说得够长的」才更新质心 — [clustering.py](https://github.com/juanmc2005/diart/blob/main/src/diart/blocks/clustering.py)；[mapping.py](https://github.com/juanmc2005/diart/blob/main/src/diart/mapping.py)
- 质心更新是直接累加（`centers[g] += embedding`），不归一化、不衰减 — [clustering.py](https://github.com/juanmc2005/diart/blob/main/src/diart/blocks/clustering.py)
- 「不可相连」约束来自分割模型：同一块里被分成两个本地说话人的，一对一指派保证它们不会落到同一个全局说话人；另外声纹提取时给「分割模型判为多人同时说话」的帧降权（改过的统计池化）— [diart README / 论文摘要](https://github.com/juanmc2005/diart)
- 官方调好的参数差别极大：DIHARD III τ=0.555 / ρ=0.422 / δ=1.517；AMI τ=0.507 / ρ=0.006 / δ=1.057；VoxConverse τ=0.576 / ρ=0.915 / δ=0.648 — [diart README](https://github.com/juanmc2005/diart)

**FluidAudio SpeakerManager**
- 默认参数：`speakerThreshold` 0.65（归属的最大余弦距离）、`embeddingThreshold` 0.45（更新声纹的最大距离，「只有高质量匹配才更新」，通常比归属阈值更严）、`minSpeechDuration` 1.0 秒（建新人的最短时长）、`minEmbeddingUpdateDuration` 2.0 秒（更新声纹的最短时长）；时长太短且对不上任何人时返回 nil（不归属）— [SpeakerManager.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/SpeakerManager.md)
- 提供 `findMergeablePairs`（找出彼此距离小于阈值、可能是同一人的簇对）、`mergeSpeaker(_:into:)`、`removeSpeakersInactive`、按条件清理（如累计时长 <5 秒的）、`isPermanent`（标成永久的人不会被自动合并或清掉）、`initializeKnownSpeakers`（预置已知声纹）— [同上](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/SpeakerManager.md)
- 流式实测结论：块之间有重叠反而更差（3s/1s 53.3%、5s/2s 55.9% vs 10s/0s 38.2%、5s/0s 39.0%），因为块变多、过度拆分 — [Benchmarks.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)

**screenpipe EmbeddingManager（Rust，源码）**
- 每人除质心外保留最多 10 份样例；匹配分 = max(与质心的相似度, 与任一样例的相似度)；归属阈值是余弦相似度 0.35（注释：「在 screenpipe 形态的评测上平衡误并和过拆」）— [embedding_manager.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/speaker/embedding_manager.rs)；[segment.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/speaker/segment.rs)
- 质心更新：`(旧 × n + 新) / (n + 1)`，n 封顶 50；样例满了以后**替换掉和质心最像的那一份**（保留多样性）— [embedding_manager.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/speaker/embedding_manager.rs)
- 人数上限：日历里有会议时按参会人数设 `max_speakers`；满员后对不上阈值的声音**强制并入最近的已有说话人**而不是新建；会议之间 `clear_speakers` 清空，防止跨会议串人；可用数据库里的质心 `seed_speaker` 预置已知的人 — [embedding_manager.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/speaker/embedding_manager.rs)；[segmentation_manager.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/segmentation/segmentation_manager.rs)
- 源码注释里的教训：上限原来是无限，长时间不开会时系统声音（播客、视频、音乐）几乎每段都新建一个簇，内存和每段的比对开销都无限增长，于是加了 1024 的硬上限 — [embedding_manager.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/speaker/embedding_manager.rs)
- 分段细节：同一人间隔 ≤0.75 秒的相邻段合并；分割模型的重叠类别单独识别 — [segment.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/speaker/segment.rs)

**其它**
- OpenWhispr：实时路径攒够 ≥1.6 秒语音后每 1 秒认一次人；<0.8 秒的段不提声纹，靠前后文传播标签；会后再跑一次批量 — [OpenWhispr 博客](https://openwhispr.com/blog/local-speaker-diarization)
- Anarlog（原 Hyprnote）的本地聚类照 pyannote 3.1 的做法：质心连接的层次聚类、按固定阈值切树，**小于 `min_cluster_size` 的簇并入最近的大簇**；阈值切出来的人数不在 `min_speakers`/`max_speakers` 范围内时改用满足范围的切法 — [anarlog clustering.rs](https://github.com/fastrepl/anarlog/blob/main/crates/pyannote-local/src/clustering.rs)
- Minutes 的改进计划里对匹配的要求：返回结构化证据（赢家、分数、第二名、差距、模型、阈值版本、拒绝原因），**每场会说话人与声纹库一对一指派**，拿不准就不给名字 — [minutes voice-enrollment.md（计划文档）](https://github.com/silverstein/minutes/blob/main/docs/plans/voice-enrollment.md)
- Speakr 的歧义处理：最佳和次佳相差不到 0.05（`AMBIGUITY_MARGIN`）视为有歧义；只有一份样例的声纹变体扣 0.03 分 — [Speakr voice_profiles.py](https://github.com/murtaza-nasir/speakr/blob/master/src/services/voice_profiles.py)

### Inferences
- 对照本项目 `SpeakerBook.assign`，可直接借鉴且改动小的几条（按性价比排）：
  1. **更新质心用更严的阈值**（FluidAudio 的 `embeddingThreshold`）：现在只要 ≥0.55 且 ≥2 秒就更新，边缘匹配（0.55–0.65）会把质心往别人那边拖，是「质心漂移 / 多人并成一人」的来源之一。
  2. **每人保留若干份样例，匹配取最大值**（screenpipe）：同一个人换语气、离麦远近不同会形成多个「声纹变体」，单质心会把它们平均掉；多样例能减少「一人多号」。
  3. **最佳与次佳的差距**（Speakr / Minutes）：两个候选分数接近时不要硬判，沿用上一位或标为待定。
  4. **人数上限 + 满员强制并入最近者**（screenpipe / diart）：会议人数通常已知或可估，上限能直接消灭「4 个人聚成 9 个」。
  5. **新簇试用期**：新建的说话人如果累计时长一直很短（FluidAudio 示例是 <5 秒；Anarlog 的 `min_cluster_size`），就并回最近的大簇，而不是永久留一个「说话人 7」。
  6. **周期性找可合并的簇对**（FluidAudio `findMergeablePairs`）：质心之间相似度超过阈值的自动并，或至少提示用户。
- diart 三套官方参数差异巨大（δ 从 0.648 到 1.517），说明在线聚类的阈值强依赖声纹模型和场景，**只能用自己的真实会议录音标定**，这一点项目的「听到」日志（每句和每位说话人的相似度）正好是现成的标定数据。
- 「延迟决策」在各家的形态是「暂定 + 确定」两级输出（LS-EEND 约 900 ms 暂定、Sortformer 560 ms 暂定、OpenWhispr 的重叠段标为 provisional、Vexa 的 draft-then-confirmed），界面上先显示暂定说话人，攒够证据再定稿。本项目接话逻辑需要即时知道「谁在说」，可以让接话用暂定结果、写记录用确定结果。

### Gaps
- 没找到公开的、针对「逐句在线归簇」各项技巧（多样例、双阈值、试用期）单独贡献多少 DER 的消融实验；上面的排序是依据各项目的设计理由和注释，不是实测。
- 指数滑动（EMA）更新质心在实时聚类里的效果：只看到 Speakr 旧版在**跨会议声纹库**里用过 0.3 / 0.7 的加权（现已改成保留原始样例），实时聚类里没有找到用 EMA 的开源实现。

## 4. 会后离线修正（全场重聚类再回填）

### Takeaway
「实时先给个临时标签、会后用全局聚类重算并回填」是主流做法，而且提升幅度很大：同一批 AMI 会议、同一打分器下，FluidAudio 的在线聚类 DER 38–56%，离线全局聚类（VBx）只有 10.6%。这是本项目目前完全没有、而收益最确定的一环。

### Cited Findings
- 同一 AMI 16 场测试集、同一仓库打分器（collar 0.25、跳过重叠）：离线 VBx 管线平均 DER 10.6%（说话人混淆 3.3）；流式在线聚类最好配置 38.2%（混淆 29.0），最差 55.9%（混淆 49.5）；官方建议「大多数应用用离线就够了」— [FluidAudio Benchmarks.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)
- FluidAudio 的离线管线 = community-1 分割 + 声纹 + 层次聚类暖启动 + VBx；聚类阈值是直接作用在层次聚类树上的欧氏距离切点（和 pyannote 一致，值越大并得越狠、人越少）；16 场里 15 场人数判对（2026-10-30 默认参数）— [同上](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)
- OpenWhispr：实时路径之外有「会后批量」一遍——sherpa-onnx 离线分离（pyannote segmentation-3.0 + CAM++，层次聚类，余弦阈值 0.5，`min-duration-on=0.2`、`min-duration-off=0.5`，人数自动），转写段按「时间重叠最多」对到分离段上；**用户手动起过名的说话人被锁定，会后批量不覆盖** — [OpenWhispr 博客](https://openwhispr.com/blog/local-speaker-diarization)
- Meetily Pro：实时录音时边录边标说话人，导入或「重新转写」的音频也会重新标 — [Meetily speaker-diarization 页](https://meetily.ai/speaker-diarization)
- Minutes：会议存盘后的转写用「独占视图」，**重叠或拿不准的区间标 `UNKNOWN` 而不是硬判给第一个出现的人**；每场会的各说话人声纹存成 `.embeddings` 旁车文件，供以后回填用 — [minutes diarization.md](https://github.com/silverstein/minutes/blob/main/docs/architecture/diarization.md)；[voice-enrollment.md（计划文档）](https://github.com/silverstein/minutes/blob/main/docs/plans/voice-enrollment.md)
- senko 的速度说明离线重算几乎没有成本：Apple M3 上 1 小时音频 7.7 秒（CAM++ 走 CoreML）；CPU（Ryzen 9 9950X）42 秒 — [narcotic-sh/senko](https://github.com/narcotic-sh/senko)
- 全局聚类算法的现成选择：pyannote / FluidAudio 用层次聚类 + VBx；senko 用谱聚类或 UMAP+HDBSCAN；sherpa-onnx 和 OpenWhispr 用阈值式层次聚类；Anarlog 用质心连接层次聚类 + 小簇吸收 + 人数范围约束 — [FluidAudio GettingStarted](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/GettingStarted.md)；[senko](https://github.com/narcotic-sh/senko)；[sherpa-onnx 示例](https://github.com/k2-fsa/sherpa-onnx/blob/master/python-api-examples/offline-speaker-diarization.py)；[anarlog clustering.rs](https://github.com/fastrepl/anarlog/blob/main/crates/pyannote-local/src/clustering.rs)

### Inferences
- 本项目已有会后流程（纪要、整理稿），在同一时机加一步「全场声纹重聚类 → 回填 `## 对话` 里的说话人」最顺。最小实现甚至不用新模型：把会中每句已算好的声纹（现在算完就丢）连同时长存下来，会后对「够长的句子」做一次层次聚类，再把短句按最近质心 + 时间邻近归进去。
- 回填时要解决「会后簇 ↔ 会中编号/用户改过的名字」的对应：做法是用会后簇质心和会中各说话人质心做一对一匹配，用户改过名的说话人锁定不动（OpenWhispr 的做法）。
- 更进一步是用 sherpa-onnx 现成的离线分离（pyannote 分割 + 声纹 + 聚类）对整场录音重跑，这样还能把一句话里中途换人的情况切开——VAD 整句归一个人是本项目「多人被并成一人」的结构性来源之一，在线聚类再怎么调也解决不了。

### Gaps
- 「同一套声纹、逐句在线归簇 vs 会后全局重聚类」在**中文会议**上的差距没有公开数字；FluidAudio 的 38% vs 10.6% 是英文 AMI，且两条路的分段方式不同。
- Speakr、Scriberr、WhisperX 本身就是纯离线（录完再处理），不存在「实时 + 会后修正」的两段式，未找到它们这方面的做法。

## 5. 重叠语音与抢话

### Takeaway
本机可行的手段有三类：(a) pyannote segmentation-3.0 的 powerset 输出自带「两人同时说」的类别，7 MB、ONNX、sherpa-onnx 直接可用，能当**重叠检测器**；(b) 端到端模型（Sortformer / Nemotron-3 / LS-EEND）直接给每个人的活动轨迹，重叠是原生支持的；(c) 麦克风一路、系统声音一路分开处理，「我」和「对方」的抢话天然不混。真正的语音分离（把重叠的两个人拆成两路音频）在调研到的开源会议应用里没有人在用。

### Cited Findings
- pyannote segmentation-3.0 在 10 秒窗口上输出 7 个 powerset 类别；screenpipe 的实现里类别序号 ≥4 的是重叠类，据此单独标记重叠段；Minutes 的说明同样写明「16 kHz、10 秒窗口、7 个 powerset 类」— [screenpipe segment.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/speaker/segment.rs)；[minutes diarization.md](https://github.com/silverstein/minutes/blob/main/docs/architecture/diarization.md)
- diart 的做法：提声纹时给「分割模型判为同时说话」的帧降权（重叠感知的统计池化），并用同块内的本地说话人互斥作为聚类约束 — [diart README](https://github.com/juanmc2005/diart)
- 3D-Speaker 的分离管线有可选的重叠检测模块（`--include_overlap`，需要 HF 令牌，即用的是 pyannote 的模型）— [modelscope/3D-Speaker](https://github.com/modelscope/3D-Speaker)
- FluidAudio 的评价：LS-EEND 高重叠场景最好；Sortformer 重叠场景良好；旧的在线聚类在「两人以上重叠」时差。重叠段保留第二位说话人，在 AMI 上能把漏检降 6–8 个点 — [GettingStarted](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/GettingStarted.md)；[Benchmarks.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Benchmarks.md)
- Nemotron-3 的所有指标都是「计重叠」口径下测的，输出是 `[T, 8]` 的每人活动概率，可同时有多人为真 — [nvidia/nemotron-3-diarization](https://huggingface.co/nvidia/nemotron-3-diarization)
- 产品层面对重叠的三种处理：Minutes——和不同说话人都相交的转写区间标 `UNKNOWN`，不硬判；OpenWhispr——重叠段标成「暂定」，点说话人标签可改；Vexa——强烈抢话时宁可发布空的说话人也不猜（约 4–7% 的行）— [minutes diarization.md](https://github.com/silverstein/minutes/blob/main/docs/architecture/diarization.md)；[OpenWhispr 博客](https://openwhispr.com/blog/local-speaker-diarization)；[Vexa README](https://github.com/Vexa-ai/vexa)
- senko 明确不输出重叠段（每时刻只报主说话人），WhisperX 自述重叠处理不好 — [senko](https://github.com/narcotic-sh/senko)；[whisperX](https://github.com/m-bain/whisperX)

### Inferences
- 对本项目最省事的一步：在提声纹之前，用 pyannote segmentation-3.0（sherpa-onnx 已有 ONNX）扫一遍这句话，**把重叠帧从声纹输入里剔掉或降权，并且重叠占比高的句子不用来更新质心**。这同时缓解「抢话时声纹是两个人的混合 → 认成第三个人或拖偏质心」。
- 同一个分割模型还能发现「一句 VAD 片段里中途换了人」，据此把片段切开再分别归属。
- 对数字人的接话逻辑而言，「这一段是重叠 / 认不准」本身就是有用信号（Minutes 的 UNKNOWN 思路）：认不准时给大脑的说话人写「有人」比写错名字安全。

### Gaps
- 没找到在 Apple Silicon 上实时运行语音分离模型（如 SepFormer、TF-GridNet 类）用于会议应用的开源实例及其速度数字。
- pyannote segmentation-3.0 单独作为重叠检测器在中文会议上的精确率 / 召回率：未找到。

## 6. 跨会议的声纹库

### Takeaway
做了跨会议认人的开源项目有 Speakr、OpenWhispr、screenpipe、Minutes、FluidAudio（SDK 层）；Meetily 明确说不需要声纹库（也就没有跨会议记忆）。成熟做法的共同点：**只在用户确认名字后才入库、保留原始样例而不是就地平均（可撤销）、分「自动贴名 / 建议确认 / 不认」三档阈值、按声纹模型隔离、同一人允许多个「声音变体」**。Speakr 现在的实现和 Minutes 的重新设计文档是两份最值得读的材料。

### Cited Findings

**Speakr（AGPL-3.0，源码）**
- 声纹库 = 每个「（录音，说话人标签）被命名一次」存一份 L2 归一化的样例，**不就地平均**；需要时再把样例聚成「声音变体」（例如同一个人在电话里和在会议室里），新声音和每个变体比、取最接近的；因为变体总是从样例重建，「删掉一份错归的样例就能完全撤销」— [voice_profiles.py](https://github.com/murtaza-nasir/speakr/blob/master/src/services/voice_profiles.py)
- 具体参数：一个标签累计语音 <15 秒不入库也不自动贴名（`MIN_SPEECH_SECONDS`）；每人每个模型空间最多 20 份样例（先丢最旧的）；相似度 ≥0.72 的样例算同一变体，最多 4 个变体；已有 ≥3 份样例的人，新样例与所有已有样例相似度都 <0.25 时判为离群（多半是名字贴错了），拒收并记日志；自动采集的样例权重 0.5；建议阈值默认 0.60；自动贴名三档 0.3 / 0.6 / 0.8；最佳与次佳差 <0.05 视为歧义 — [同上](https://github.com/murtaza-nasir/speakr/blob/master/src/services/voice_profiles.py)
- 「嵌入空间」概念：只在同一个模型产生的声纹之间比较，换模型后旧声纹留在「旧空间」不混用 — [同上](https://github.com/murtaza-nasir/speakr/blob/master/src/services/voice_profiles.py)
- 旧版做法（仍留在代码里）：平均声纹按「新 30% + 旧 70%」加权更新；置信度 = 最近样例与声纹的平均相似度 × min(1, 样例数/5)，只有 1 份样例时固定 0.5；注释写「声纹相似度通常在 0.6–0.99」；声纹是 256 维，由 WhisperX 服务返回 — [speaker_embedding_matcher.py](https://github.com/murtaza-nasir/speakr/blob/master/src/services/speaker_embedding_matcher.py)
- 合并两位已存说话人：声纹加权合并、片段转给目标、所有显示源名字的录音改显示目标名字、删除源 — [speaker_merge.py](https://github.com/murtaza-nasir/speakr/blob/master/src/services/speaker_merge.py)

**OpenWhispr（MIT，官方博客）**
- 本地 SQLite 三张表：`speaker_profiles`（声纹 BLOB + `sample_count`）、`speaker_mappings`（笔记 ↔ 声纹的对应）、`note_speaker_embeddings`；声纹是 CAM++（英文 VoxCeleb 版）512 维 — [OpenWhispr 博客](https://openwhispr.com/blog/local-speaker-diarization)
- 三档：余弦 ≥0.70 自动确认；0.55–0.70 给出「这是 Alice 吗？」的建议，可确认或忽略；<0.55 保持匿名 — [同上](https://openwhispr.com/blog/local-speaker-diarization)
- 更新用累计平均：`(旧均值 × 样例数 + 新声纹) / (样例数 + 1)`；给说话人起名会**回溯改写过去会议里同一声纹的标签**，用户锁定过的对应关系跳过 — [同上](https://openwhispr.com/blog/local-speaker-diarization)

**screenpipe（源码）**
- 说话人和声纹存数据库，实时聚类器可用库里的质心预置已知的人（`seed_speaker`）；HTTP 接口有：列出未命名说话人、改名、搜索、取说话人的音频样例、删除、**标记为「幻觉」**（不是真人的声音）、合并两位说话人、找相似说话人、改判（`ReassignSpeakerRequest`，带 `propagate_similar`——默认把相似的片段一并改判，以及作用范围 `scope`）和**撤销改判** — [screenpipe routes/speakers.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-engine/src/routes/speakers.rs)；[segmentation_manager.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/segmentation/segmentation_manager.rs)

**Minutes（MIT）**
- 已实现：声纹库 `voices.db`（SQLite，文件权限 0600），**按声纹模型 id 隔离**——community-1 的声纹绝不和 CAM++ 注册的声纹悄悄比较，换模型要重新注册；命令行注册要求样本里只有一位一致的说话人，有歧义的样本不动已有声纹 — [minutes diarization.md](https://github.com/silverstein/minutes/blob/main/docs/architecture/diarization.md)
- 重新设计文档（**计划，不代表已全部上线**）里的结论，按原文归纳：
  - 单个可变的混合向量「丢失来源且不可逆」，要改成不可变的 `voice_samples` 行（人、精确的模型 id 和维度、归一化声纹、来源等）；
  - 「被动注册」（用户确认一次名字就把会议里的声纹并进库）有**投毒风险**：贴错一次就把错的声音混进声纹、悄悄拉低以后的匹配；因此被动采集默认关闭，采到的只是「隔离的候选」，不影响匹配，须满足多项条件才晋升；
  - 主动注册：一段约 20–30 秒自由说话的样本，带质量门槛（低信噪比 / 不一致 / 多人的拒收）；调研结论是有效语音至少约 20 秒，3 段各约 10 秒最好；
  - 回填旧会议时**不要用「最大的簇就是我」来推断**，要锚定在用户手动确认过的标注上；
  - 匹配要一对一、带差距、拿不准就保持匿名（「不确定 → 匿名」好过贴错名字）；
  - 隐私：全部在本机，声纹是本地 0600 SQLite 里的向量，从不上传，一键可删；标为受限的会议默认不参与被动注册（声纹是受限内容的生物特征衍生物）；分开的开关：是否存每场会的声纹、是否采候选、候选保留天数、是否保留非本人的声纹（默认否）
  — [minutes voice-enrollment.md](https://github.com/silverstein/minutes/blob/main/docs/plans/voice-enrollment.md)
- README 提到另有「同意执行」的架构设计 — [Minutes README](https://github.com/silverstein/minutes)

**FluidAudio（SDK）**
- `initializeKnownSpeakers` 预置已知声纹（可选覆盖 / 合并 / 跳过，尊重「永久」标记）；`upsertSpeaker` 可带原始声纹列表、更新次数、时长；文档建议在用户自我介绍（"My name is Alice"）时把默认名改成真名 — [SpeakerManager.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/SpeakerManager.md)；[GettingStarted](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/GettingStarted.md)
- 端到端模型做预注册：Sortformer 最好（靠说话人缓存，能高置信地把人对上，声音相近也行）；LS-EEND 在声音太像时会注册失败，没有按槽位锁定的接口；「跨会议记住说话人」一项，旧的声纹聚类方案反而评为最好 — [GettingStarted](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/GettingStarted.md)

**没做或不走这条路的**
- Meetily：「不需要注册的声纹库」；说话人识别是 Pro 功能（1.8.2 起），免费的社区版（MIT）没有 — [Meetily speaker-diarization 页](https://meetily.ai/speaker-diarization)；[Meetily README](https://github.com/Zackriya-Solutions/meetily)
- Scriberr：分离后端是 pyannote 或 NVIDIA Sortformer，界面有说话人改名对话框和说话人映射接口；仓库里未见声纹库相关文件 — [rishikanthc/Scriberr](https://github.com/rishikanthc/Scriberr)
- FunASR：编号只在一段录音内有效，不是注册识别 — [FunASR README](https://github.com/modelscope/FunASR)

### Inferences
- 对本项目的落地顺序建议：先存「每场会每位说话人的质心 + 累计时长 + 声纹模型 id」（成本几乎为零，相当于 Minutes 的旁车文件），再做「用户改名 → 入库一份样例」，最后才做「下次会议自动认出」，且自动认出一开始只做**建议**（界面上名字带个待确认的状态），不直接贴。
- 声纹随设备 / 房间变化这件事，开源里唯一明确处理的是 Speakr 的「声音变体」（最多 4 个）和 screenpipe 的多样例；FluidAudio 实测 CAM++ 跨会议 EER（3.55%）比会内（2.85%）差。对本项目而言：会议室拾音（一个麦收所有人）和线上会议（系统声音）应视为两个变体，不要平均成一个向量。
- 本项目的隐私边界（`Settings.guarded`）需要覆盖声纹库：替别人开会且没勾「可以谈我的其他项目」时，是否允许用其它会议积累的声纹来认人、这场会的声纹是否入库，要明确规定——Minutes 的做法是受限会议默认不入库。

### Gaps
- 「同意」的具体交互（比如入库前是否要告知被录的人）：开源项目里只看到 Minutes 提到有同意执行的设计文档，本次未读其内容；其余项目都只强调「本地、可删」，没有针对被识别者的同意流程。
- screenpipe 的跨会议匹配阈值和它对设备变化的处理细节：只看了实时聚类和接口，数据库侧匹配逻辑未读。
- Anarlog（原 Hyprnote）是否有跨会议声纹库：仓库里有 `KnownSpeaker` 类型，但具体行为未核实。

## 7. 不靠声纹的线索

### Takeaway
最有效、成本最低的非声纹线索是**音源分路**：麦克风一路一律算「我」，只对系统声音那一路做说话人区分（OpenWhispr 就这么做）。其次是**日历**（参会人数当聚类上限、参会人名单当改名候选）和 **LLM 从对话内容推名字**（Speakr 做成了一个按钮，且可限制只能从已存的名字里选）。读会议平台的「谁在说话」标记目前只在入会机器人类项目里见到（Vexa 读 Teams 页面上的说话指示）。

### Cited Findings
- OpenWhispr：麦克风音频**始终按来源标成用户本人，不做声纹匹配**；只有系统音频走说话人拆分 — [OpenWhispr 博客](https://openwhispr.com/blog/local-speaker-diarization)
- OpenWhispr：接了 Google 日历后，说话人选择器里预填参会人的姓名和邮箱，一键把说话人对到参会人 — [同上](https://openwhispr.com/blog/local-speaker-diarization)
- screenpipe：日历里的会议开始时，按已知参会人数设置聚类的人数上限（源码注释：「日历辅助的分离」）；会议结束后恢复默认并清空 — [segmentation_manager.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/segmentation/segmentation_manager.rs)；[embedding_manager.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-audio/src/speaker/embedding_manager.rs)
- Speakr 的「从对话中识别」：把逐字稿交给文本模型，线索是「别人称呼某人时提到的名字」「自我介绍」「对话里直接出现的名字」，返回 `{说话人标签: 名字}` 的 JSON，认不出的留空；默认只给还没名字的说话人起名 — [speaker_identification.py](https://github.com/murtaza-nasir/speakr/blob/master/src/services/speaker_identification.py)；[Speakr 用户文档](https://murtaza-nasir.github.io/speakr/user-guide/transcripts/)
- Speakr 的「上下文自动贴名」：当转写服务不返回声纹时，把用户已存的说话人名字作为候选交给 LLM，**模型只能原样选用这些名字或留空，不能引入新名字**；代码还会检测并纠正模型把映射写反（`{名字: 标签}`）的情况 — [speaker_identification.py](https://github.com/murtaza-nasir/speakr/blob/master/src/services/speaker_identification.py)
- FluidAudio 文档建议：听到自我介绍时更新说话人的名字 — [GettingStarted](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/GettingStarted.md)
- Vexa（Apache-2.0，入会机器人，支持 Google Meet / Teams / Zoom）：Teams 采集模块读页面上每位参会者的「说话音量蓝框」（`[data-tid="voice-level-stream-outline"]`）等样式 / aria / class 标记，去抖后产生每人的开始 / 停止说话事件，作为给混合音轨的**提示**（不依赖字幕）；约每 2 秒重发一次当前说话人，方便中途接入的消费者；自述选择器是防御式写的，因为 Teams 的 DOM 会随版本变 — [Vexa teams-capture README](https://github.com/Vexa-ai/vexa/blob/main/core/meetings/modules/teams-capture/README.md)
- Vexa 的归属不保证：强烈抢话时绑定器发布空的说话人而不是猜，约占 4–7% 的行 — [Vexa README](https://github.com/Vexa-ai/vexa)
- Minutes：把配置里的本人名字（及别名）锚定为「我」，即使是没有日历参会人的单人录音；对 Teams / Zoom 桌面端有可选的自动通话录制和「原生通话采集」的分轨恢复（`recover-stem`）— [voice-enrollment.md（计划文档）](https://github.com/silverstein/minutes/blob/main/docs/plans/voice-enrollment.md)；[Minutes README](https://github.com/silverstein/minutes)
- Meetily 社区版同时采集麦克风和系统声音（带压限和防削波），数据库迁移里有一个 `speaker` 字段 — [Meetily README](https://github.com/Zackriya-Solutions/meetily)
- 3D-Speaker 提供基于文本语义的说话人转换点检测模型（中文 BERT），即用「说的内容」辅助判断换人 — [modelscope/3D-Speaker](https://github.com/modelscope/3D-Speaker)

### Inferences
- 本项目是「数字人参会」，自己说的话（TTS 输出）本来就知道是谁说的；如果采集链路能区分「本机麦克风」和「会议软件输出」，那么线上会议里「我（真人）」这一位可以完全不靠声纹——这直接减少一位需要聚类的人，也消除「我」被拆成多号的问题。
- LLM 推名字和本项目已有的大脑很契合：会中听到「我是张三」「李四你怎么看」时，可以作为**改名建议**（界面上待确认），而不是直接改——Speakr 把结果「填进表单供检查」，没有自动生效。注意项目约定里「会上的话是不可信输入」：LLM 推出的名字只能当建议，且要像 `rename` 那样清洗。
- 读会议软件界面上的「正在说话」标记，在本机非机器人的形态下要靠 macOS 辅助功能接口，调研到的开源桌面应用里没有人这么做；Vexa 的经验说明这类选择器随版本频繁失效，维护成本高。

### Gaps
- 通过 macOS 辅助功能 API 读 Zoom / Teams / 腾讯会议 / 飞书「谁在说话」的开源实现：没找到。
- 腾讯会议、飞书、钉钉等国内平台的发言者事件获取方式：没有找到开源项目涉及。
- Meetily 的 `speaker` 字段具体是不是「麦克风 / 系统」的来源标记：只看到迁移文件名，未读内容。
- Anarlog 是否按麦克风 / 系统声音分路标注说话人：仓库有本地 pyannote 聚类，但分路逻辑未核实。

## 8. 交互：说话人标签的呈现、改名、合并、改判、回溯

### Takeaway
开源竞品里已经形成的「标配」是：通用编号 → 改名一次全场生效 →（有声纹库的）回溯到历史会议；做得细的是 screenpipe（改判可连带相似片段、可撤销、可标「不是人声」）、OpenWhispr（三档置信度 + 「这是 Alice 吗？」确认 + 手动改的锁定）、Speakr（改名弹窗里每位说话人配一段原话样例、声纹建议带置信度、LLM 认名按钮）。普遍缺的是「把一句话改判给别人」的批量手段，以及对错误合并的撤销。

### Cited Findings
- **呈现**：Speakr 默认 `SPEAKER_01`、`SPEAKER_02`；点工具栏的识别按钮打开弹窗，**每位说话人旁边显示一段他说过的话**，填名字后全场替换 — [Speakr 用户文档](https://murtaza-nasir.github.io/speakr/user-guide/transcripts/)
- **改名全场生效**：Meetily Pro——「改名一次，整份记录里的名字都更新」；Speakr——名字替换整份转写里的通用标签 — [Meetily speaker-diarization 页](https://meetily.ai/speaker-diarization)；[Speakr 用户文档](https://murtaza-nasir.github.io/speakr/user-guide/transcripts/)
- **改名回溯历史会议**：OpenWhispr 起名后回溯改写过去会议里同一声纹的标签，用户锁定过的跳过；Speakr 合并说话人后「每一条显示源名字的录音都改显示目标名字」— [OpenWhispr 博客](https://openwhispr.com/blog/local-speaker-diarization)；[speaker_merge.py](https://github.com/murtaza-nasir/speakr/blob/master/src/services/speaker_merge.py)
- **合并**：Meetily Pro——一个人被拆成两个标签时可合并成一位；screenpipe——`merge_speakers(保留的, 并入的)` 接口，另有「找相似说话人」接口帮用户发现该合并的；FluidAudio SDK——`mergeSpeaker` + `findMergeablePairs`；Speakr——账户里的说话人管理页可合并、删除、全部清空，每张卡片显示名字、被识别次数、最后使用时间 — [Meetily 页](https://meetily.ai/speaker-diarization)；[screenpipe routes/speakers.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-engine/src/routes/speakers.rs)；[SpeakerManager.md](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/Diarization/SpeakerManager.md)；[Speakr 用户文档](https://murtaza-nasir.github.io/speakr/user-guide/transcripts/)
- **单句改判**：Speakr 的编辑器里点任一段的说话人字段可改，下拉里建议已存的说话人、边输边筛（文档没说是否连带其它段；「查找替换」不改说话人名）；OpenWhispr 点说话人标签可改，重叠段默认标为暂定；screenpipe 的改判请求带 `propagate_similar`（默认把相似片段一起改）和作用范围，并返回旧归属以便**撤销** — [Speakr 用户文档](https://murtaza-nasir.github.io/speakr/user-guide/transcripts/)；[OpenWhispr 博客](https://openwhispr.com/blog/local-speaker-diarization)；[screenpipe routes/speakers.rs](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-engine/src/routes/speakers.rs)
- **置信度的表达**：OpenWhispr 三档（自动确认 / 「这是 Alice 吗？」可确认或忽略 / 匿名）；Speakr 的声纹建议带置信分并分高中低三级（<0.6 低、<0.8 中）— [OpenWhispr 博客](https://openwhispr.com/blog/local-speaker-diarization)；[speaker_embedding_matcher.py](https://github.com/murtaza-nasir/speakr/blob/master/src/services/speaker_embedding_matcher.py)

- **不是人声的簇**：screenpipe 可把一位「说话人」标记为幻觉 — [同上](https://github.com/screenpipe/screenpipe/blob/main/crates/screenpipe-engine/src/routes/speakers.rs)

### Inferences
- 对照本项目现状（设置窗口里能改名，没有合并和改判），按项目自己的设计原则（主窗口不加文字和按钮、每个操作都有接口和稳定 id）可借鉴的最小集合：
  1. **合并两位说话人**（接口 + 设置窗口里的操作），合并后回填当场记录——这是「一人多号」最直接的补救，所有做说话人的竞品都有。
  2. **改名时附一句原话 / 可播放的样例**（Speakr、screenpipe），否则用户不知道「说话人 3」是谁。
  3. **改判一句话**（接口优先）：并且像 screenpipe 那样可选「连同相似的句子一起改」和撤销；改判结果应反馈给聚类（被改判的句子从原簇样例里拿掉、加入新簇），否则同样的错会重复犯。
  4. **用户动过的都锁定**（OpenWhispr）：手动改过名 / 改判过的，会后重聚类和自动贴名都不能覆盖。
  5. **待确认状态**：跨会议自动认出的名字、LLM 推出的名字，用颜色或位置表达「待确认」，不要加说明文字（符合项目「状态用颜色和位置表达」的原则）。
- 给 AI Agent 的接口面可以直接参考 screenpipe 的那一组：未命名列表、改名、合并、相似查询、改判 / 撤销、取样例、标记为非人声。
